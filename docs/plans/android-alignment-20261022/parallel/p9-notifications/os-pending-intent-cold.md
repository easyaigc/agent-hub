## Exact boundary

The writer uses the production `NativeChatNotificationPlatform.forAcceptance(...).prepareAsync/post`, its original opaque ticket and the original immutable PendingIntent. The Android NotificationManager must return the actual own row with matching package/UID, exact tag/id, channel, title, summary, UUID subtext and original PendingIntent identity. The new reader then uses Android UiAutomation to open the shade and perform exactly one ACTION_CLICK on a unique verified SystemUI row. It does not directly launch an Activity or send a PendingIntent as a substitute for that first click.

The reader is a **new instrumented app process with no Activity**, after the writer PID has exited. Existing `prepareReader` establishes the fixed lease permit before the OS tap. The first Activity is created by the system's original PendingIntent. This proves the first Activity/default-store boundary in a fresh instrumented process; it does not prove the OS itself spawned a previously absent app process. That stronger process-spawn scenario would require a separate observer and an additional narrow pre-Activity permit design, and is not claimed here.

The original cold receipt remains `claimed`: the existing seed helper commits its original immutable receipt hash, and Platform.post itself does not call the Delivery/store finish boundary. Actual OS submission evidence is the real NotificationManager row and its matching SystemUI node/cropped image. This scenario does not claim the Delivery.finish path passed in the same run. Existing OS delivery tests cover that separate component boundary. Synthetic event, client and backend provenance are kept distinct from actual OS posting/click evidence; no real push, vendor integration, Host/runtime/model result is implied.

## SystemUI selector and blocked paths

The selector requires root/row owner `com.android.systemui`, exact resource `com.android.systemui:id/expandableNotificationRow`, a visible/enabled/clickable ACTION_CLICK row and visible text matching all three original UUID metadata/title/summary fields. It requires exactly one candidate. The resource assumption comes from the [AOSP row layout](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/packages/SystemUI/res/layout/status_bar_notification_row.xml); it is an explicit runtime prerequisite, not an OEM/API37 compatibility claim. The test enables and restores its UiAutomation view-id reporting flag as described by the [AccessibilityNodeInfo API](<https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#findAccessibilityNodeInfosByViewId(java.lang.String)>).

Read polling is bounded to fifteen seconds, 2,048 nodes and depth 48. There is one click attempt, no coordinate injection, expansion guess, direct Intent launch, fabricated callback, PendingIntent first-open fallback or post replay. Missing/ambiguous/changed/inaccessible rows or a rejected ACTION_CLICK fail the path and emit a bounded attempt/failure record. Do not continue a queue against an incomplete armed/selected lease. Preserve it and request a separately reviewed exact-lease inspection/seal plan if needed; this Spec does not introduce a general failed-router cleanup capability.

The test uses [UiAutomation's system action API](<https://developer.android.com/reference/android/app/UiAutomation#performGlobalAction(int)>) and [NotificationManager's own-notification snapshot](<https://developer.android.com/reference/android/app/NotificationManager#getActiveNotifications()>). It saves no full shade dump or full-screen image. Only a verified own row is cropped and retained. No other notification text, title or attachment is exported.
