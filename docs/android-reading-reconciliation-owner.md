# Android reading reconciliation after Session reset

F49/F50/F56 source delta `AndroidReadingRestoreOwnership`. Status: implementation and boundary assertions; Native, interactive UI and real device acceptance remain unexecuted until Root schedules the exact integrated candidate. The previous Source55 case3 readback files are outside this change.

The existing Android ledger already isolates complete agent/Host/workspace/runtime/thread identities, excludes Codex login metadata from machine identity, keeps other agents' account constraints, ignores foreign-reader acknowledgements, retains seen notice tombstones and removed connections' rows, and counts unread conversations independently of badge display. iOS `ThreadReading`/`MobileUnreadBadge` and generated KMP `ReadingPolicy` remain the reference. No unread rule, schema, wire type, second event consumer or second ledger is introduced here.

The gap is in Android's asynchronous Session writer. `NativePhoneReadingStore.reset()` invalidated UI publication but left a queued worker able to call the ordinary ledger reconciliation after it obtained the storage lock. That worker could replace the restored scope set or merge an obsolete newer head, even though its result was no longer displayed. Cancelling a coroutine alone cannot revoke a synchronous storage transaction already waiting on a lock.

`NativeReadingWriteFence` gives each Session writer a revocable owner. Reset invalidates it synchronously and cancels the captured worker. `NativeReadingLedger.reconcileOwned` checks it after loading under the existing storage transaction lock, immediately before in-memory mutation. A stale owner changes no scopes, head, read watermark, pending acknowledgement or notice, and saves no ledger. Only in-memory reconciliation holds the owner monitor; parsing, encryption and disk I/O stay outside it. A mutation already admitted before invalidation has the same transaction linearization rule as existing visible-read leases. Later owners can reconcile normally. Backgrounding alone continues to preserve valid metadata and existing reading lifecycle guards; it does not delete or reset the ledger.

Root integration is limited to the P7-owned files `NativeReadingWriteFence.kt`, `NativeReadingLedger.kt` and `NativePhoneReadingStore.kt`. The ledger patch changes its transaction wrapper and adds an owned overload; Root's separate P9 `reconcileNotificationActive` addition must remain. `NativeSessionStorage`, `MainActivity`, `MobileSession` and the P9 coordinator are not modified. Keep the existing `phoneReading.reset()` call at the restore/session replacement boundary. A shared-file integration requiring different timing must be reviewed by Root; do not copy an old whole Session or Storage file.

## Assertions and Native selectors

The pure fence tests cover a storage-lock wait followed by reset, repeated reset without owner revival, and independence between phone owners. The ledger assertions execute the production ledger, identity and shared reading policy. Host runs use an explicitly synthetic transactional IO port and codec adapter; they cannot establish Keystore, Android lifecycle or real network behavior.

Root's new Native selectors, using real encrypted storage in task-owned synthetic namespaces, are:

- `com.agenthub.android.NativeReadingEpochLedgerTest#queuedRemovedRuntimeCannotOverwriteRestoredScopes`
- `com.agenthub.android.NativeReadingEpochLedgerTest#queuedOldHeadCannotReviveRestoredReadOrQuestion`

Both block a real storage transaction, queue the old owner, invalidate it and install current state before releasing the lock. The first preserves a removed runtime's original read/pending record while keeping another runtime counted. The second preserves a restored read watermark and a seen question across reopen and delayed delivery, then accepts a genuinely newer event. Neither reads an approval as a decision, sends a Host acknowledgement or creates a command.

The test-only `NativeReadingEpochWorkers` hands the fixture the exact executor, Future and named Thread before submission. After releasing the transaction lock, each worker gets one bounded exit wait: orderly shutdown, executor termination and an actual Thread join within the original five-second total budget. No `shutdownNow`, Future cancellation or worker interruption is used. Original scenario/Future failures remain primary, with exit failures suppressed. A timeout or interrupted observer leaves termination unconfirmed even if the Future is done or the thread later exits. Unknown handles and their storage remain reachable in `NativeReadingEpochLedgerTest.retained[fixtureId]`; storage is not retired and no execution file or alias is touched. `workers.json` records exact identities, live state, budget, elapsed wait and exit failure for Root. This is a per-process diagnostic handle, not a resumable operation or permission to replay it.

Each Native run uses only its new private `no-backup/reading-epoch-<fixture>` directory and matching unique alias. After all owned workers physically exit, storage may be retired. Successful assertions then remove only the verified execution ciphertext, namespace and alias. Immutable private cleanup intent/completion receipts precede/follow each destructive step; missing completion means unknown, never retained-key proof. A failing mutation or receipt is not retried. Small worker/cleanup/result evidence remains for Root capture with a six-hour review point; Root then removes that exact evidence directory. Scenario failures retain the untouched execution data and alias; cleanup failures report actual completed/unknown states. Cleanup receipts do not establish Native body success. The source-only auxiliary worker/receipt checks do not establish Android encrypted-storage or UI acceptance.
