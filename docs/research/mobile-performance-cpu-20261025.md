# iOS 持续 CPU 开销续修（2026-10-25）

承接[状态IO与CPU基准](mobile-performance-io-20261025.md)。上一阶段会话逻辑写入下降65.7%、原生只读滚动hitch ratio均值约6.00→1.51ms/s，但CPU没有下降：混合33.85%→34.05%，无活动XCTest的联网静置14.08%→14.50%，混合最高热状态仍为2。本阶段继续处理CPU，不把写入收益等同于发热解决。

CPU候选的三客户端完整流程已通过，但尚未证明整体CPU收益：平均占用34.05%→33.39%，实际采样时间更长，累计CPU时间159.45→171.48秒。p99移动帧26.70→17.51ms，最大移动帧45.18→52.35ms，超过50ms由0/1783变为1/1800；不能只选改善的指标宣布本轮性能通过。系统滚动与同一已完成回复的零输入尾帧诊断另列。

## CPU数值与参照口径

本报告CPU来自进程累计user+system CPU秒除以实际覆盖墙钟秒，100%表示一个核心持续忙碌；30%不是整机30%容量，也不是电池耗电30%。连续回复、富文本和切换期间的30%不能单独判定正常或异常；回复结束后联网静置仍持续12%～15%，以及每两秒状态检查点，是继续定位的依据。应同时比较相同操作完成后的累计CPU秒、等待时长、逻辑读写、真实系统卡顿、唤醒及热状态，不能靠延长等待压低平均值。

没有在这台手机、相同网络、历史规模和操作下采集其他商业聊天App的开发者性能轨迹，因此不提供“微信/ChatGPT应为X%”的竞品数字。Apple建议按真实操作录制、修复并重新验证CPU瓶颈，见[Addressing CPU bottlenecks](https://developer.apple.com/documentation/xcode/addressing-cpu-bottlenecks)；可采用官方滚动hitch ratio参照（下文），但它不能换算成通用CPU百分比。App功耗还涉及屏幕、GPU和网络，CPU优化与发热缓解的关系须由后续同条件结果检验，见[官方功耗分析流程](https://developer.apple.com/videos/play/wwdc2025/226/)。

## 定位依据

准确物理iPhone、独立验收bundle及PID的30秒Time Profiler取得4214ms采样权重，其中主线程1496ms；设备进程核对未观察到本任务Runner残留。状态保存包含802ms、HostService.load包含491ms、输入区body包含233ms、targetKey包含181ms；这些是有重叠的包含权重，不能相加，也不能当作独占函数CPU百分比。

采样包含`Published.subscript.getter`、SavedSession复制/销毁和ARC，以及输入区重建。代码同时存在相同运行态/会话摘要反复赋值、纯事件恢复游标推动界面发布的路径。校验与持久化仍保留，优先减少不改变呈现值的工作。

## 实现与辅助验证

- 大型SavedSession改为普通值存储，写入仍通过`objectWillChange`预先通知；不再通过Published getter为读取一个成员复制整个大值。没有直接使用原`$saved`发布者的调用方，ObservedObject成员绑定仍支持。
- 完整运行态采用合成Equatable，所有存储字段参与比较；相同运行态、摘要、问题数量和同步提示不重复发布。回执处理、历史修复、故障展示及原2秒检查点保持。
- 仅既有同一完整目标/线程的游标进度更新不驱动界面；新key、目标或线程变化仍发布。游标值仍立即更新到同一SavedSession，仍进入原持久化快照，不改变未知输入查询与命令前落盘。
- 首次历史代次确认、建议新鲜性确认显式通知界面，避免控制可用性依赖已删除的重复赋值。

原生辅助程序编译生产属性/方法片段及实际运行态DTO，检查绑定、不可变快照、游标持久化、作用域变化、首次确认和48个运行态字段变化；目标桩仅隔离发布机制，不替代协议身份验收。完整原生手机混合流程与原Electron owner结果仍须另验。

Android没有Swift Published的大结构体读取路径，本轮不改其生产状态实现；既有共性缓存/富文本/隐藏动画修复保持，不新增Android真机功耗结论，A6保持暂停。

## 系统滚动指标

相同老历史、关闭业务数值探针，以`XCTOSSignpostMetric.scrollDecelerationMetric`各测三次。两次开始前数值采样均确认热状态0；普通原生流程及阅读锚点检查通过。基线hitch ratio为[0,0,4.529]，均值1.510ms/s；CPU候选为[6.696,8.932,0]，均值5.210ms/s。这是回升，不能只凭p99移动帧改善宣布渲染通过。准备以候选→基线的反向顺序复测，同样保持准确物理设备、独立App与相同系统指标；复测不包含模型输入。

Apple对hitch ratio的建议为低于5ms/s通常良好、5～10ms/s应调查、超过10ms/s应优先处理，见[官方说明](https://developer.apple.com/videos/play/tech-talks/10855/)。这不是其他聊天App的实测CPU基准，也不能把CADisplayLink帧间隔等同于实际错过渲染期限的时间。

## 最大单帧续查

本次52.35ms位于第17步“重开已完成回复”，该对话为同一原输入生成的200行回复。同区间持久化准备包含约1.71ms，其中存储键捕获约1.56ms，不能将相互包含的时间相加，也不能据此解释整段52ms。探针只记录部分主线程路径中≥1ms工作并有256条保留上限，不能用空白区间证明没有其他工作。对同一已完成原对话再做零输入读取、24手势和准确PID的Time Profiler，结果在完成后补入。

更早87.41→115.01ms是含导航和预热的累计最大值，没有该原帧时间戳，不能唯一还原。此前可复现的长帧调用栈已定位到目标键／字符串桥接和关闭侧栏仍重建，见[原长历史报告](history-thermal-20261024.md)。本轮严格窗口、逐步骤和系统hitch ratio分别保留，不修改旧口径来制造改善。

手机继续充电，无电池耗电、瓦数或温度摄氏度结论。正式App和共享Host未由本任务部署。

## 真实持续回复主线程诊断补证

在同一候选App可执行文件上，以Instruments负责唯一一次App启动，独立原生Runner发起一条新的600行原输入。此时原对话已有三轮1400行历史；原owner确认新输入只有一条、xhigh、无工具、完成，4手势和实际切入空草稿均仍在该原轮运行区间。随后重开并20手势。该场景是更长历史和附带采样开销的诊断，不是前述800行基线的等价资源复测，输入未重放。
