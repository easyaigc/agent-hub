# 后台持久化的精确内容复用

## 适用范围

2026-11-23：经授权的私有 Main profile 将后续优化指向可替换状态及历史缓存持久化。原始 profile、回执、本机路径与进程连续性证据仅留私有任务目录，不进入源码或公开产物。本文只描述实现和合成验证；目标 Host 的 CPU、内存与任务连续性仍由部署负责人暖态复测，不能用受控基准宣布实机已解决。

调用链为 `RuntimeSession.emit/saveBackground` → `RuntimePersistence.schedule` 定时回调 → `saveState`，以及 `dirty` → `drainOne` → `writeHistory`。元数据保存不含线程正文，但仍可能携带大量附件、回执和消息链接；历史缓存在独立文件。旧路径即使候选元数据最终判为未变，也会再次完整 JSON 编码、候选摘要和实际账本读回。历史重复 dirty 也会编码并原子发布相同内容。

本轮仅优化 macOS 的这两条后台路径，不改变调度延迟、状态、事件率、队列、正文、媒体、授权、同步命令或落盘格式。Windows 继续原路径，不把 POSIX 边界 fixture 视为 Windows 原生验收。

## 有界且保守的快照

快照只包含此前候选的独立结构和不可变原始值，不保存许可、上游大对象或执行上下文。每次命中都遍历当前值，比较原键顺序、数组长度、类型和全部字段，检测相同数组/对象中的原地修改；不会仅凭引用相同判为不变。Proxy、getter、toJSON、非普通原型、稀疏或含非枚举索引的数组及超预算内容退回原序列化路径，不降低业务内容上限。抓取在 JSON 前执行，避免自修改 getter 导致保存值和快照不一致，也不额外执行 getter。

单项保守权重最多96MiB，总权重192MiB、最多65项；结构节点单项262144、全局524288，单项属性最多100万、深度64。权重计入原始字符串UTF-16长度、键与结构成本，不宣称是精确RSS上限。淘汰按LRU，关闭时释放；显式采集时的固定标签同时统计状态/历史命中和快照拒绝，不输出值或目标。没有新增磁盘缓存、迁移、历史删除或未知输入重放。

元数据只在已经观察到稳定 no-op 后准备快照，避免每个真实变化都复制大型状态。命中仍要求原 durableHead/ledgerHead 一致，实时检查私有文件，每次调用仍在入口校验真实完整账本字节和当前 writer nonce，命中时也核对当前文件身份及私有权限；没有发布则省掉候选 JSON、候选摘要和对自己写入的重复读回。同步 `save`、`saveRead` 和 `close` 继续原完整路径，显式命令不因命中省略发布/fsync。失败后的原 durability 失效、重试、退避、deferral 和版本 fencing 保持。

历史快照只在已观察到稳定后台元数据后启用；元数据持续真实变化时走原历史写入路径，避免每次变化都另行复制结构和计算缓存摘要。历史命中核对当前文件身份、私有权限、纳秒时间及真实字节 SHA。读取使用 no-follow fd，检查前后 fstat、精确长度及额外字节探测；固定256KiB缓冲区，读预算超512MiB即退回原写入，而非拒绝业务内容。缺失、替换、损坏、权限或正文变动都退回原路径。快照在写入依赖回调前抓取，发布后的外部修改不能靠后记录的stat取得内容相等证明。下载、附件许可、来源/版本及撤权仍沿各自原实时检查，不依赖本快照。

## 验证与交付

边界命令：`node --test --test-concurrency=1 scripts/runtime-persistence-background.test.mjs`、`node scripts/runtime-persistence-smoke.mjs` 及 `pnpm check`。覆盖后台候选工作消除、同步读/命令/关闭屏障、当前账本篡改、外来nonce、原地修改、一次性getter、历史文件丢失及发布后损坏修复、超快照预算仍完整落盘。原错误和安全断言保持，不能为性能改测试门槛。

`scripts/runtime-persistence-benchmark.mjs` 使用确定性合成状态，约605线程、22000附件、3500回执、4096消息链接、36–37MiB元数据及三份各约11MiB历史，顺序独立进程对照相同数据和事件率。预热后测量CPU、墙钟、阶段次数、实际发布/fsync和结果摘要；另测真实变化，保留完整数据及必需屏障。冷堆用于显式模拟保留压力，不冒充目标机堆布局；合成CPU比例不是目标Host占比。

2026-11-23 受控单次配对：macOS、Node24.22.3，基线为`135199ed`的原持久化模块，35次稳定和35次真实变化事件，间隔850ms，另保留1536MiB冷JS堆。元数据实际38375937字节，三份历史各约11MiB。稳定阶段进程CPU用时5953.262→2275.326ms（−61.8%），Main3736.398→2259.411ms（−39.5%），JSON编码88→0次、历史发布53→0次。真实变化阶段进程CPU8192.852→7820.643ms（−4.5%），Main5198.051→5015.122ms；两组均35次状态发布、53次历史发布、70次fsync。最后同步读/保存/关闭均为2次状态发布、1次历史发布、1次关闭fence和6次fsync，完整状态及三个历史摘要相等。短同步阶段CPU有自然波动，不能把单次比例当成保证。早期逐次捕获历史的草案在长变化窗口约增加13%CPU，已拒绝，并收窄为仅稳定元数据后启用；未改安全预期。

部署仍使用规范源码构建、经Gitea main及既有GitHub同步链发布的统一冻结包。核准确提交、整包及实际ESM指纹，保留原Host身份、状态、密钥、授权和操作ID；主会话只在可安全退出/落盘并对账在途操作时安排Host程序正常切换，原桌面和模型任务继续。回滚使用原r5程序及当前兼容状态，不覆盖runtime.json或重放未知输入。原[有界采集工具](host-cpu-profile.md)可按新程序身份再次显式arm，由原部署负责人采集并核闭合回执。
