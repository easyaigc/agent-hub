# 已发布交互回退核对（2026-11-19）

本次由用户报告子 Agent 页面变成内嵌长文本触发。对照已发布 iOS 114 的冻结源、原验收记录与当前 `98841a6b`，核对 115 组合及后续主线。源码、原验收、本次辅助检查、当前原生交互和正式安装分别判断；旧版通过不等于新版通过。Android A6 暂停保持。

## 已确认的根因

1. 已发布 114 使用 `SubagentMessageView` 的单行状态入口；点击后才挂载 `SubagentDetailView`。主／子记录共用 `ChatTimelineEntryView`，按原消息边界显示正文和工具组。冻结源中的这部分生产代码和原完整过程验收文档与发布输入摘要一致。
2. 较早主线仍是 `EasyWorkSubagentMessageView`：预览末尾六行，点击“展开”直接把拼接的提示词、命令及输出挂到主列表。
3. `8ed6e931`（`feat(ios): preserve released workflows in build 115`，经 Gitea PR #188 集成）只给旧卡片追加 `SubagentHistoryAction`，另外新增 `SubagentHistoryEntryView` 和完整记录弹窗。读取能力补回了，原入口、按需挂载和主子共用渲染的行为没有完整迁入。
4. 原有完整子过程原生验收没有随生产行为整体迁入；旧主线的内嵌展开测试仍保留。现有 Node 边界检查和编译不能检出入口或布局回退，默认原生基线也没有子 Agent 场景。组合记录已明确写着完整记录弹窗交互尚未验证，因而不能据该记录宣布已保留原完整交互。

另查出 `ccbfe36c`（2026-11-06）在 `RootView.sheets` 中新增重复 `.usage`／`.projectGit` 分支，前置分支仅允许 EasyWork，遮蔽原通用入口；Swift 只发出 `case is already handled by previous patterns` 警告而继续构建。本次原生额度场景确实打开空白 sheet，保留了失败回执，随后恢复唯一通用路由。故该问题不全部始于 115，115 的兼容整合也未识别和修复它。

这是已发布行为在源码组合时被局部恢复、回归断言又未覆盖所致。不能归因于用户操作、Codex 原始输出变化，或把有 API／编译成功视为界面已兼容。现有证据不足以推定截图实际安装包的版本，正式 App／Host 本次没有被替换。

114 子 Agent 后端三个关键文件与 `963d39ec` 一致，而该提交不是当前 HEAD 的祖先；`8ed6e931` 已进入当前主线。说明这不是用户记忆与新设计冲突，而是发布现场与开发主线分叉后，人工恢复语义不全。恢复时又遗漏相应原生及边界测试，使这部分差异没有被门禁阻止。
