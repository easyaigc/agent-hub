# Stage 11: actual panel visibility to the existing reading ledger

Base `e6ea5683ab93525fea29345eee1422eb0e0e19c0`. This is a view port and owner integration proposal, not completed Session/P9 wiring. Every new component parameter defaults to null. Without an explicit binding, no observer, report or ledger write is installed and existing rendering paths are unchanged. No new ledger, event consumer, persisted model, command or transport is added.

The reference iOS RootView reading task first requires active scene, settled sidebar, no covering sheet, latest-message geometry and no history load. SessionStore.recordVisibleContent then joins approval/question `(notificationRequestId ?? id, turnId)` and proposed plan `(id, turnId)` to notice requestId/runId. That implementation is not proof that every matching panel is geometrically visible: it uses the chat-bottom visibility boundary. Android's new port deliberately reports only an actual mounted panel with a current native geometry proof. Host NotificationObserver emits approval/question/plan with requestId/runId and no operationId; its IDs include kind, run and original request/plan. The UI ID is not substituted when notificationRequestId exists. Unknown operationId, wrong run/kind/thread, seen notices and conflicting duplicate IDs fail closed.

`NativePanelNoticeVisibility` is an explicit input containing full reading target/thread, the existing ledger's unseen notice snapshot, foreground/uncovered flags, a stable render epoch and a UI callback. It has no I/O. Use one remembered binding per immutable view frame; changing target, connection/certificate/selection epoch, notices, covering state or rendered original must replace it. forTarget uses the same ThreadReadingIdentity key as the ledger, preserving the Codex historical-account policy. The original is the full immutable MobileApproval or MobileProposedPlan object, not an ID-only approximation. The view holds only references to current models and metadata; reports must never serialize/log their question or plan text.

ExecutionPanels and InlineToolApproval accept the nullable input. Actual normal/expanded async ApprovalPanelContent is wrapped; the collapsed async question-count row is not a reading witness. ProposedPlanReview accepts it only around the expanded actual Markdown plan text. Its generic implementation prompt or closed disclosure is not evidence. If the same plan is instead rendered in the message timeline, that separate renderer still needs an owner hook; no inference from the generic prompt is made here. PlanPanels changes are limited to that signature and expanded-body fragment.

The native helper requires the complete wrapped content rectangle to survive ancestor/window clipping, a focused attached native window, a RESUMED view-tree lifecycle, explicit foreground and explicit uncovered, and two current frames. Scroll clipping, detach, native focus loss, pause, model/binding replacement and disposal retract the proof. A collapsed or oversized approval/question remains unread; this conservative whole-card policy is a known gap for reading a long card in segments, not a completed long-card reading feature. A plan witness is its expanded actual body. No title-only, percentage or selected-chat shortcut is used. Arbitrary same-window overlays and ancestor opacity are not discoverable from geometry; the parent must set uncovered false when drawer interaction starts (including settlement/cancelled drags), while sheets/other cover or render transitions are unsettled. Dialog window focus additionally retracts the covered underlying view. A focused question dialog may use the same exact frame only when its own surface is declared uncovered.

`NativeNoticeVisibilityFence.Proof` is irrevocable after retraction/disposal. Its isCurrent is useful for scheduling only. The atomic integration must use NativeNoticeReadGuard.ifCurrent around the ledger's short in-memory mutation, not merely check then asynchronously write. The guard must never enclose encryption, disk I/O, suspending code or an external call. The report callback is expected to be a small UI adapter, not a synchronous ledger reader. No approval answer, plan implementation, task command or original input is sent by reading.

The shared boundary remains owner work:

1. Parent/P9 publish unseen notice metadata from **phoneReading.ledger**, through the already existing consumer/projection. Read any encrypted metadata off the UI thread, bind the result to the original target/thread/connection/render epoch, and discard late snapshots. Do not instantiate another production ledger or add another event stream.
2. On a fresh selected render frame, call the same NativeReadingLifecycle.present with latest position and the known notice IDs. The existing NativePhoneReadingStore.visible body path currently calls present without notice IDs; it must preserve the current frame's notice inventory. Otherwise it resets them to empty. Session foreground, cover, target and connection invalidation remain authoritative. Notice reporting must not mark the reply position, and body reading must not acknowledge unseen panels.
3. On a true report, revalidate the original approval/plan and complete current target/thread/connection/render frame. Obtain visibleNotices for that exact notice ID with the report's guard, then call the existing same-ledger readVisible on the existing background writer. Publish through its existing snapshot/changed path so P9's atomic mayPresent suppresses the same seen event. Unknown results are not commands and must not be replayed as task inputs. False/disposal invalidates the view guard immediately, even if the parent callback is delayed or throws.
4. ThreadReading requires an optional guard on notice leases, checked inside ifCurrent. Its body lease remains guard-free and retains its old behavior. The tree-outside proposal has an exact observed source SHA and proposed target SHA below. It also leaves body leases with empty notice IDs so body reading cannot acknowledge offscreen notices. It is not applied here. Other shared files have only named hook contracts and source/hook-text hashes; their final whole-file targets depend on the active P9 owner implementation, so no invented target-file SHA is provided.
