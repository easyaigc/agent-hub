# P9 Android notification recovery v2 source candidate

Status: implemented source and auxiliary checks; parent integration and real DEV remain unverified. This slice follows the optional Host contract in [the server candidate](recovery-v2-server.md) and does not change iOS v1, EasyWork, APNs/vendor readiness or background delivery promises.

The foreground monitor negotiates the exact v2 capabilities and bounds. Only a capabilities HTTP 404 before v2 adoption permits the old v1 path. An unknown version, malformed response, or an existing v2 record with unavailable capabilities blocks new writes. A fresh disabled installation creates neither identity nor journal. The existing v1 unknown intent is preserved and continues only its v1 status read; it cannot be upgraded into a v2 acknowledgement.

Every attempted v2 mutation is an encrypted original containing stable UUID, original epoch/device/target/public key/preferences/subscription generation and canonical SHA-256, plus the captured authorization fingerprint. It is saved as unknown before the one HTTP attempt. A cold restart queries exactly that UUID and epoch under the original authorization. Absent or epoch mismatch is still unknown; no automatic POST or replacement UUID follows. Direct/queried receipts settle only their own original. Rejected settings do not automatically generate another intent for the same desired preference revision.

A separate human off action may create a higher-generation revoke, including for an absent device or while an earlier register is unknown. That receipt confirms the new off action; the earlier unknown remains unchanged and visible. A subsequent on action needs a newer preference generation. Delayed lower-generation receipts cannot replace the current subscription. V1 revoke is blocked locally after v2 adoption; parent removal/credential rotation must use the retained original snapshot and the explicit v2 off action before discarding access.

Original pages have fixed epoch/high water, contiguous sequence and strict raw event fingerprints. The full page and every outcome are persisted before P7/platform effects. An interrupted processing outcome becomes unknown without another presentation call. Inactive originals and expired nonactionable originals receive durable terminal outcomes. Actionable `stale` means unverified, remains `waiting-host`, does not call P7/platform, and does not advance the cursor. A later read refreshes only dispositions and the complete active set for the original interval; it preserves original bytes and the captured high water. Filtered originals still pass through the required P7 port so local alert preferences do not suppress unread bookkeeping.

A retention/epoch gap produces an explicit offer, never a zero cursor. Accepting it is a separate persisted `feed-reset` intent with one stable acceptance UUID. Snapshot pages are processed by index; the old live cursor stays until all original outcomes and the full ordered canonical event-array hash match the original receipt. Only then does the live baseline advance. An expired snapshot is never reposted: a read of the original live cursor may produce a new gap offer requiring another explicit acceptance. Older completed or obsolete reset receipts cannot reactivate a snapshot. A reset reconciles retained records and cannot prove recovery of pruned unknown history.

All journal/large JSON and canonical hashing run on IO. The existing required P7 port owns read/active policy, and the existing delivery adapter owns Main/platform calls. Parent presentation/configuration fences survive suspensions. A process-wide v2 mutex serializes retained-credential actions and foreground workers, while storage still uses the existing snapshot → operation lock order. Original receipts may settle after presentation invalidation but cannot publish a newer draft/cursor/target.

## Parent integration contract

- Keep the existing P7 `mayPresent` and `MigrationTombstones` guard in `NativeChatNotificationStore.claim`; this slice does not edit that file.
- `NativeChatNotificationHttp` implements the optional v2 commands; the existing monitor selects the negotiated path. Keep required `NativeChatNotificationForegroundPort` and exact-target draft-preserving route; no default unread adapter or new execution port.
- Settings page adds optional `onExplicitDisable(hostId?, savedRevision, actionId)`. It runs only after the exact off/exclusion preference save. Null host means the saved global off; select each retained complete target, derive `NativeChatNotificationRecoveryController.targetActionId(actionId, fullTarget)` for each target, then call `monitor.explicitDisable(snapshot, savedRevision, stableTargetActionId, freshFence)`. A repeated callback must retain the same action UUID.
- The independent `NativeChatNotificationRecoveryStatus` renders typed monitor reports. Its off callback must first persist host exclusion/off with a new preference generation, then use that saved revision and the callback UUID. Its gap callback calls `monitor.acceptGap(snapshot, offer, actionId, freshFence)` only after the confirmation dialog. It exposes no conversation replay/control action.
- Shared MobileSession/MainActivity/NativeSheets/Manifest, central feature/design/acceptance tables, localization registry and migration entry points remain parent-owned. Product strings for the new status/dialog are listed in the parity delta for localization. These entry points are not claimed integrated or visually verified by this workline.
- Register the new local journal as unsupported/nonportable until the P7 owner deliberately wires its archive validator. Never omit it to obtain a successful migration. See [the journal and migration contract](recovery-v2-android-journal.md).

## Auxiliary evidence and limits

`node scripts/mobile/check-chat-notification-recovery.mjs` compiles the shipping Kotlin canonical decoder, fixed HTTP client, both foreground journals, identity, local receipt store, monitor and controller against installed cached dependencies. Its 41 JVM vectors include five frozen Node/Kotlin canonical values, lost ACK/cold original query, explicit off, unknown old v1 preservation, generation/epoch fences, owner loss/restore, raw fingerprint/size bounds, P7 filtered events, active-set refresh, legacy outcome dedupe, cursor high water, reset hash/expiry and actual loopback fixed HTTP operations. Only the JVM storage and Looper ports are synthetic; this proves neither Android encryption nor Main/IO scheduling. It never contacts a real Host.

The acceptance APKs compile 15 `NativeChatNotificationRecoveryTest` scenarios using isolated actual Keystore/AtomicFile namespaces and four `NativeChatNotificationRecoveryUiTest` scenarios using owned MainActivity/NativeTestForeground. They are compiled only. The UI scenarios use synthetic callbacks, preserve the default installation, and do not request permission, post notices or start Host/model work. Existing 45 shipping v1 wire/HTTP auxiliary vectors remain a separate regression.

No Android native execution, real Electron/phone/model task, notification arrival/playback, vendor, Windows, A6 or formal Host deployment was performed. Parent lease must bind actual source/APK/environment fingerprints before claiming any real acceptance. The [parity delta](recovery-v2-android-parity-delta.json) supplies F52 assertions, shared-table/localization/migration follow-ups and exact source hashes without editing parent central tables.
