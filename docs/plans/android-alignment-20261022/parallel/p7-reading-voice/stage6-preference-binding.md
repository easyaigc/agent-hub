Preferences now have distinct session-only, loading, saving, persisted and failed states, plus read/write failure kinds. A valid read acknowledges either a stored enum or the defined absent-record desktop default, without writing a new record. A user choice made before binding or while a read is pending stays authoritative in the Session. Read failure cannot authorize a write over unread/corrupt source. Writes are serial and coalesced; persisted becomes true only for the actual current value after an acknowledged save or verified matching readback. A saved acknowledgement for a different/older choice cannot mark the new choice persisted.

Background or Session restoration pauses the preference owner, invalidates callbacks and cancels work. A mutex keeps even a deliberately non-cancellable old backend call from overlapping a replacement read/write. On resume, incomplete writes are first read back. If an unknown write actually committed the current desired value, a matching read acknowledges it without a duplicate save. If the read disagrees with the new desired value, the UI retains that choice as unpersisted until an explicit retry. A failed read/save never claims persistence; retry first validates the source and only then saves a pending explicit choice. `refreshPreferences` verifies source state; `retryPreferences` permits the explicit pending save; `resumePreferences` coalesces unfinished recovery rather than rebinding.

The settings page shows loading/saving/failure honestly and exposes an explicit recovery action. Its choices form one native selectable group. These states do not start recognition, change an active capture's route, ask permission, contact a Host or change sealed recording behavior. The original-file phone transcription gap and the explicit-new-recording distinction remain unchanged.
