## 优先级和交付顺序

优先级按数据安全、用户完整闭环、依赖和真实使用频率重排。已确认的数据丢失、重复操作、错误目标、越权或恢复破坏问题列 P0，立即插入对应工作包；没有此类新失败时按下表推进。任何一项环境缺失仅阻塞依赖它的验收。

N 编号保留原档案归属；C 编号仅表示新的调度顺序。**完整迁移不再排在日常核心链路之前**；迁移的全部原范围和已实现内容保留，涉及数据丢失/错误授权的修复仍插入P0，升级发布仍受迁移安全门槛约束。

### N1 分三次完整里程碑收口

1. **N1.1 文件完整性和兼容性**：冻结同一来源，认证覆盖版本、清单、内容、顺序和精确结束；验证容量边界和有界资源；旧格式继续按各自版本上限读取。现有 Android v2 已有分帧 AEAD，待办是新大容量/原件清单路径的完整认证集成，不能写成从未加密。关闭 source/sink/锁失败必须保留原回执；实际可保存、可重读、可验证的同一文件才算完成。
2. **N1.2 完整资料导入与激活**：按[24 组系统资料](acceptance.md#迁移的-24-组系统资料)逐组规定保留、重建或不迁移；目的端发布与激活、全部 owner 交接、失败补偿及不同 PID 冷恢复。系统 URI/通知注册、安装凭据和旧授权不能靠迁移直接获得执行权，原操作仍只读核对。
3. **N1.3 用户闭环和双端兼容**：实际系统导出/导入、密码/来源/损坏/取消/另选/重复导入/结果未知、长字段和短视口、原录音只读列表及保存。iOS/Android 的格式版本、容量、资料域和身份策略逐项列兼容矩阵；仅已共同实现的格式做实际互通，其余明确拒绝并保留原资料，不能把两种平台封包认作同一 wire。

每个里程碑以用户可复验的完整结果交付。内部 helper 修复作为该里程碑子任务，不再将几十个组件通过分别包装为“完整迁移完成”。

## 并行边界

见[五条工作线](workstreams.md)。当前工具并发上限为4（含总控），采用总控+3路执行轮转，不声称5个执行会话同时运行。N1 与 N2 的原件/锁/存储规则由同一负责人收口；同一文件不并行改。N3/N4 共享阅读版本与通知身份，协议先统一后分别改系统入口。N5 可独立推进 Provider/传输及 UI，N6 负责共同原意图和回执边界，N7 的展示/搜索/额度可独立开展。集成者统一审查公共层、冲突和双端影响，统一验收与交付，不能把同一原操作分给多个执行方重放。

## 开发、验收与进度更新规则

- 每次开工先拉取并冻结最新 AgentHub main 和 EasyWork master；新增iOS/Android及EasyWork相关提交分别补来源账本和契约，映射F/UI/验收四格，记录替代关系。未合入/未提交候选不冒充主线。
- 同一工作线一次推进一个完整功能；同时做双端差异与双Provider契约/实际结果验收，登记反馈并完成该功能退出门后才领取下一项。不同功能可按不相交边界并行。本机可推进的工作持续做，依赖缺失登记到 pending，未知结果保留原 ID 和原回执。
- 每阶段完成时先保存档案和证据，更新 progress 中的功能状态、实际通过范围、失败/未验、源码/包/环境指纹、下一步和负责人，再提交短期 `codex/` 分支。通过后在 Gitea 提 PR 合入 main，核实远端合并 SHA 后清理已合并分支；主线是唯一持续集成入口。
- 用户已授权按阶段连续推进，不逐次询问是否继续。只有新增缺失权限或必须人工完成的外部条件才集中说明；普通待验不停止其他包。
- 进度回报只报本轮完成、尚未完成、下一优先项和交付链接。阶段档案保留方法/断言、原失败与证据，计划不追加过程流水账。

C1 原回执校验限定范围已交付；当前优先收口 C2-SUB 子代理与长详情，按实际四格结果与[进度](progress.md)调度，不逐次确认。合并后结束本项执行子会话并回收独占临时资源；正式侧栏聊天只通过可用的正式归档接口清理，接口缺失/未决结果单列，不修改官方历史。
