## 1. 目标与代码基线

交付原生 Android Agent Hub，完整覆盖当前 iOS 的功能、页面结构、产品视觉和交互状态。iOS 继续使用 SwiftUI；Android 使用 Kotlin / Jetpack Compose。同一目标、同一输入和同一事件序列应产生相同的业务结果、能力限制和操作提示。

规划时本地提交为 `7cf3583928481eaa3a0531f51aa88d4f0f7b13b7`，远端查询当时鉴权失败。A0 已恢复只读查询并合并远端 `main` 的 `e80e5a2911fa4aa0a3daafae73d261aed12853ac`，保留期间产生的用户变更；合并起点为 `a0f2e04c4bc72190f45191cfe9a970bb056c5755`，完整输入摘要见阶段记录。新增自动发现、VPN 分类、非阻塞问题和历史分页相应进入双端范围。

基线读取了 `README.md`、架构、可行性、开发、协议、通知文档，并核对 `apps/ios/Sources`、通知扩展、原生测试与现有协议检查脚本。迁移按窄模块进行，不以整文件翻译作为架构；旧规划的文件规模不作为新输入的测量结果。

当前范围包含 Codex 和 EasyWork。必须覆盖直接 Host、只读历史、托管／共享／原桌面模式，以及 EasyWork 局域网和中继路径；不同 Provider 的实际能力继续分别判断。现有文档中较早的“仅 Codex”“Android 不纳入首版”和未完成状态保留为历史背景，本计划与[双端功能清单](../product/mobile-parity.md)定义本次扩展范围。

平台最低版本暂定 Android 8.0 / API 26，iOS 保持 17.0。这是产品支持范围建议，A1 按依赖兼容性与实际目标设备核定。`compileSdk`、`targetSdk`、JDK、Gradle、AGP、Kotlin 和 Compose 的具体版本在 A1 查询官方兼容表后固定，不用未经验证的“latest”。默认规划有 GMS 和无 GMS 两类真机，首批具体机型、无 GMS 推送供应商和签名／分发账号在 A0 记录。

## 2. 技术方案

采用 **Kotlin Multiplatform（KMP）共享业务核心 + 两端原生 UI + 版本化协议 + 共用设计规格与验收场景**。KMP 可以只共享逻辑，iOS 通过原生 framework 调用，适合渐进接入现有 SwiftUI。[官方原生 UI 与逻辑复用教程](https://kotlinlang.org/docs/multiplatform/multiplatform-integrate-in-existing-app.html)

具体决策、替代方案与迁移边界见 [ADR-002](../adr/0002-native-mobile-shared-core.md)。A1 已建立下列工程、同步共享规则、向量及原生编排入口；完整状态机与协议对照继续由 A2 实施：

```text
apps/android/                       Android 原生 App、平台适配与原生测试
packages/mobile-core/               KMP 领域模型、规则、状态机与共同测试
packages/protocol/schemas/           既有管理／通知 Schema，补齐实际 HTTP 契约
packages/protocol/fixtures/mobile/   同步规则输入与结果已建立；事件向量待 A2
design/mobile/                      设计 token、文案与合成视觉基线
scripts/mobile/                     原生构建与回归入口已建立；契约及真实 DEV 按阶段补齐
```

JS 工作空间继续只使用 pnpm。Android / KMP 由受版本控制的 Gradle Wrapper 构建，iOS 由 Xcode 构建；根 pnpm 脚本统一调用原生构建入口。Gradle 是原生编译工具，不引入 npm、Yarn 或 Bun。共享 Kotlin 模块不导入 TypeScript 源码，Node 服务不改写成 Kotlin。

| 复用层   | 实施内容                                                                                                           | 保留的平台边界                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 业务核心 | 完整目标身份、能力策略、草稿／不可变提交、回执与创建状态机、队列与计划前置条件、事件恢复、消息归组、未读与通知策略 | 页面生命周期与原生控件                                   |
| 协议     | 复用已有管理 v1、通知 v1 的 Schema 与 manifest；补实际 Codex HTTP 输入／返回契约；三语言共用正反例                 | Codex HTTP v1、EasyWork v2 的 wire 映射各自留在 Provider |
| UI 规格  | 同一信息架构、布局 token、状态文案、图标语义、合成样例与页面编号                                                   | SwiftUI 与 Compose 分别渲染；系统界面单列差异            |
| 验收     | 一个功能 ID 对应两端实现和相同场景断言；公共核心测试一次，两端原生与真实 DEV 分别执行                              | 手机、OS、Host、桌面、模型与推送供应商分别记证           |

A1 就要求 Android 和 iOS 实际调用同一公共规则，不能将“只在 Android 使用的 Kotlin 库”记为双端复用完成。A2 开始逐项替换 iOS 对应规则；每迁入一项便回归 iOS 并删除旧规则的生产路径。网络与系统服务通过窄接口注入，首轮保留 iOS URLSession、Keychain 和通知扩展，避免同时重写传输与存储。

## 3. 分阶段实施与验收门槛

阶段按 A0 → A1 → A2 → A3 → A4 → A5 → A6 → A7 → A8 推进。每阶段可以拆成多个小变更，业务范围不因拆分被删减。负责人是角色，实施时在阶段记录中落实到具体人员／聊天及提交；本次未分派远端任务。

执行时按用户要求，每阶段全部适用模拟器验收通过后才进入下一阶段。A0 对当前 iOS 进行基线验收；A1 起 Android emulator 与受影响的 iOS Simulator 分别执行。真实模型、原桌面、真机系统与推送仍按下表另记结果，不以模拟器替代。

## 4. UI 完全遵照 iOS 的落实方式

以当前运行代码和合成数据的 iOS 画面为对照，旧设计文档只补充交互意图。详见[双端 UI 一致性规格](../design/mobile-parity.md)。逐页比对布局、层级、颜色、字体层级、间距、圆角、按钮位置、状态文案、交互及深浅色；不采用另一套 Material 默认产品布局。

Android 原生系统权限、照片／文件选择、分享、系统返回和通知外观由系统提供。将这些差异列入平台表，保持入口、业务行为、结果与草稿保护一致。Android launcher 的数字角标不具有所有设备统一保证；App 内未读汇总必须准确，桌面角标按机型实际记录。不能将系统限制悄悄算作全功能通过。

## 5. 通知是后端开发项

现有 `packages/protocol/src/notifications.ts` 的 delivery 为 `foreground-only | apns`，`apps/relay/src/push-server.ts` 实现 APNs。安卓无法直接使用这条投递路径。

A7 为通知引入受限、注册式 `PushProvider`：保留观察、加密、绑定、去重、撤销和账本语义，Provider 只负责认证、提交与供应商回执。显式声明设备平台和投递能力，通知契约按现有 v1 严格 Schema 的兼容要求选择可并行协商的新版本；旧客户端和 APNs 保持可用。不得给严格 v1 直接塞入会被旧端拒绝的字段。

有 GMS 的目标以 FCM 为首选；无 GMS 的首批设备必须接入实际选定的供应商并真机验证。FCM 客户端有 Google 环境要求，所以不能把 FCM 接入当作所有安卓手机已覆盖。[FCM Android 要求](https://firebase.google.com/docs/cloud-messaging/android/get-started)

只投递最小路由与密文，手机验证目标并解密后呈现；避免供应商自动展示与 App 展示重复。前台／后台的数据消息处理和系统调度分别验证，不以常驻 WebSocket 维持后台推送，也不把工作调度器当实时推送。离线、强制停止、节电限制和供应商不可用时保留真实状态，回前台权威补同步。[FCM 接收路径](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)

## 6. 检查、真实 DEV 与完成定义

当前已存在的命令：`pnpm check`、`pnpm build:ios`、`pnpm check:mobile-env`、`pnpm check:agent-contract`、`pnpm check:notifications` 及专项原生／真实模型脚本。只改计划文档时做格式、链接和内容核对；实施涉及 TypeScript／工具链时执行 `pnpm check`，涉及 iOS 时执行 `pnpm build:ios` 及受影响专项。

根命令按阶段落地；下表的实现状态不代表完整产品或 CI 已通过：

| 命令                       | 验证内容                                        | 状态                                               |
| -------------------------- | ----------------------------------------------- | -------------------------------------------------- |
| `pnpm build:android`       | Gradle debug APK，Android 与公共核心依赖构建    | A1 已实现                                          |
| `pnpm check:mobile-core`   | Kotlin/JVM、Kotlin/Native 公共规则及 Swift 边界 | A1 已实现，A2 扩展状态／契约与异步边界             |
| `pnpm check:mobile-parity` | 功能 ID、场景／UI／证据关联及功能变更清单维护   | A2 已实现检查，产品证据独立维护                    |
| `pnpm test:android`        | 指定专用 emulator 的原生仪器测试                | A1 已实现，后续阶段扩展场景                        |
| `pnpm test:live:android`   | 专用真实 Host／Electron／模型／Android DEV 编排 | A4 已实现创建／回复／Host 重启子集；完整场景待补齐 |

CI 分为 Node、公共核心、Android 构建／instrumentation 和 macOS iOS 构建／原生回归。当前只有 Node 与 iOS 构建 Job，当前 Git 服务能否执行既有工作流仍须核对；不写“CI 已通过”代替实际日志。公共核心不会因仅 JVM 测试通过就被认为 iOS 已验证。

真实验收采用[双端验收场景与记录规范](../acceptance/mobile-parity.md)。保护原任务和用户数据，使用专用聊天、状态目录、端口与依赖／构建目录。每个操作固定完整目标，桌面独立核对原 owner、输入、附件和运行结果；远端平台测试仅在确有该环境验证需求时按 `AGENTS.md` 协调。此次规划不需要跨电脑分派。

“完整安卓版本”要求 F01–F59 的适用项全部实现，UI01–UI13 全状态对齐，S01–S18 真实场景逐平台完成，iOS 采用共享规则后的回归通过。缺设备、供应商、签名、OIDC 或证据时按未验收／未实现报告；不删除失败行，也不以仅前台提醒代替后台通知交付。
