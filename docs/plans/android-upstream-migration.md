## 4. 每个提交的处理规则

### 4.1 先建立完整清单

源头确定后，以固定完整 SHA 计算所有未包含的提交，按父提交先于子提交的顺序登记，而非只按时间排序或只筛选 `apps/ios`。Host、Adapter、协议、Relay、脚本、Skill、依赖、测试和文档提交全部纳入审查，避免遗漏隐含依赖。

可用的只读盘点命令为 `git rev-list --reverse --topo-order HEAD..<frozen-source-sha>`，随后逐项读取父提交、完整差异和文件列表。源分支继续变化时，新增提交进入下一轮冻结清单，不在正在验收的输入中自动漂移。多个来源先分别固定 SHA，再合成去重且父子有序的队列。

台账每项必须包含：序号、来源仓库／分支、完整 SHA 与 parents、原提交标题、范围及 diff 摘要、前置提交、冲突文件和处置、功能 F／页面 UI／场景 S 编号、iOS 与 Android 各自适配、Host／协议兼容性、辅助与真实证据、截图检查、迁移前后 HEAD、实施及验收状态、回退点、交付提交和推送回执。状态分别为待分析、待合并、迁移中、验收失败、验收通过、已提交、已推送；缺项不能算完成。

### 4.2 一次只引入一个来源提交

在受保护且清洁的迁移检查点上，对单个源 SHA 进行保留祖先关系的增量合并。默认使用 `git merge --no-ff --no-commit <source-sha>`；实施前必须确认相对当前 HEAD 只有这一个尚未引入的来源提交。若还有未登记祖先，先补清单及父提交，不能借一次合并引入整串提交。

普通提交和 merge commit 都登记；merge commit 要额外检查其冲突解决引入的差异，不能只检查第一父提交标题。只有补丁内容相同也不自动跳过：登记等价证据并保留明确来源关系。不以 squash、整目录覆盖、批量 cherry-pick 或全文件 ours／theirs 替代逐项审查。

当前提交的 Android 迁移和兼容修复属于这一项，可形成有明确来源关联的本地修复提交；修复完成前不继续下一个上游提交。若上游提交本身是不可编译的中间态，记录阻塞及最小修复，不把后续多个提交捆入后称“逐提交通过”。

### 4.3 先保证两端行为，再封存本项

每项先确定上游的预期行为，再对照本地已有功能，更新[功能清单](../product/mobile-parity.md)、[UI 规格](../design/mobile-parity.md)和[共同场景](../acceptance/mobile-parity.md)。iOS 同时保留已合入上游的变化和当前分支有效的 KMP／A5 修复；Android 按相同断言实现对应功能，而非只做到编译或 HTTP 可达。

发现 Android 对应功能缺失时，必须在本项补齐或明确阻塞；不能简单写“以后 A6 实现”后将本项记为通过。平台专属行为须写明另一端不适用的依据，仍验证共同业务断言。用户暂停 A6 的状态不因此改为进行中。

按用户最新要求，每项完成顺序为：审查与适配 → 必要构建／边界检查 → 本机双模拟器、小米及 iOS 适用原生与真实 DEV → Mac Mini 24G 独立 iOS 验收并回收核实 → 检查原图／更新台账及完成范围 → 正常迁移提交并推送 main／独立核对远端 SHA → 下一步。失败保留原始结果、停止队列，只修复当前项；不能用后续修复覆盖失败证据。M4 汇总最终交付，不延迟各步骤已要求的推送；检查点推送也必须明确不是 A5 或整个迁移阶段完成。

## 7. 回退、交付与 A6 暂停

每项合并前保存已验收检查点和数据格式兼容范围。仅当前自有未完成合并可用 `git merge --abort` 回到该检查点；已提交迁移通过追加回退／修复提交处理，保留来源与失败记录，不强制重置、丢弃 stash 或重写共享历史。涉及数据格式时先验证备份及双向兼容，不能只回退二进制后直接读取不兼容数据。

正式 Host／桥接升级遵照[统一分发规范](../development.md#host桥接工具与-skill-的统一分发)：先构建验证，保留各机身份／私有配置及旧产物，再按同一包更新，逐机验收。回退只针对本轮产物及所需的数据转换，不覆盖账户、密钥、原 Codex 配置或其他聊天。

完成后更新逐提交台账、双端功能表／UI、架构或协议变化以及[阶段进度](../acceptance/android-stages.md)。A5 是否封存依据最终新输入的完整门槛；当前 1/7 记录继续作为原输入证明。推送前重读远程；新增提交重新排队、逐项处理，不能盲目 pull。推送后独立 `ls-remote` 核对分支 SHA，不强推。
