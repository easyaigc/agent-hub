# Real Android notification system boundary preparation

This stage adds fourteen executable native cases using `NativeChatNotificationPlatform`, the installed `NativeChatNotificationSoundProvider`, real `NotificationManager` channels/active notifications and real `ContentResolver`/kernel file descriptors. It does not use a fake SystemPort to prove OS behavior. Local assembly is auxiliary only; every physical/API26/API37 result starts as not-run in [native-system-plan.json](native-system-plan.json).

## Resource ownership and production path

`NativeChatNotificationAcceptanceScope` requires a debug build and the exact independent package `com.easyai.agenthub.android.acceptance`, plus a canonical UUID. It derives a fixed `P9-native-system-<uuid>` encrypted storage namespace, `native-chat-acceptance-v1.<uuid>.` channel/tag prefix and canonical `content://<package>.chat-notification-sounds/acceptance-v1/<uuid>/<sha256>.wav` sound URI. It accepts no filesystem path, arbitrary namespace, method or credential. The protected `.acceptance.easywork` sibling is rejected before storage creation.

The explicit platform factory constructs its sound library with that same scope/store. The registered provider resolves only this fixed acceptance path in that exact debug package and reconstructs the same encrypted namespace. Ordinary production constructors retain `native-chat-v1.` and `/v1/<hash>.wav`; release and other packages cannot use the acceptance path. The provider remains nonexported, grantUriPermissions and read-only. No capability, health, vendor enrollment, backend endpoint, permission bypass or second unread ledger is added.

Actual foreground delivery receives the existing required reading interface, reconciles the fixture event on IO, uses the real platform, and claims the original opaque ticket in the same encrypted store. The fixture's reading decision and count seven are synthetic boundary inputs; they do not establish the real P7 ledger's unread calculation. The permission-cycle controller uses only the existing named synthetic recovery fixture commands, a fixed synthetic epoch/clock and the same encrypted store. It never contacts a Host/model or retries an unknown original.

## Parent execution sequence

1. Freeze the parent's integrated app/test source, APK and runner fingerprints. Confirm the manifest prerequisites against [native-system-parent-prerequisites.json](native-system-parent-prerequisites.json). The isolated P9 baseline lacks the parent's permission/provider entries; its APK assembly cannot prove installed registration.
2. Supply an exact canonical `p9SystemLease` UUID. Missing lease means skipped, not verified. Execute Provider with `p9SystemPermission=unchanged`. These five cases register no channel and post no notification.
3. On API33/37, record the exact acceptance package's previous grant state and relevant flags. Parent alone changes permission to denied and executes Denied with `p9SystemPermission=denied` and a fresh `p9SystemCycle` UUID. The cycle method refuses an existing identity/marker instead of replaying a prior attempt. It preserves only that cycle's private store for the explicit grant phase.
4. Parent grants this exact package, then executes Granted with `p9SystemPermission=granted` and the same cycle UUID. The persisted denied event remains terminal; only event two posts; original operation hash and identity remain unchanged; no new original submit is made. Successful completion cleans the cycle store. Restore the previous authorization/flags in a finally path, including on test failure. The tests themselves never grant/revoke, click a dialog, adopt shell permissions, change volume/DND or touch another app.
5. On API26, execute Provider five and Granted six non-cycle cases. Two Denied methods and the Granted cycle are API33+ only: eleven eligible, three not applicable. API33 and API37 each have fourteen eligible cases, recorded separately by source/APK/device fingerprint. If the app is globally blocked or the expected permission is wrong, the explicit phase fails rather than pretending OS post success.

Keep original instrumentation results and app-private proof rows from `files/acceptance/P9-native-system/<lease>/`. Each fixture attempt writes a fresh proof filename, so a failure cannot replace an earlier cycle result. Proof-row counts are not method counts; multi-scope cases produce more rows and the pure package-guard case needs no resource row. Only successful method results with cleanup confirmation support a native pass. Rejected/missing prerequisites, skipped SDK branches, failed cleanup and failures remain separate.

## Assertions and limits

The granted cases inspect actual posted private/public notification fields, badge number/channel flags, original stored receipt, canonical existing PendingIntent identity/creator/immutability, target/event/run-scoped cancellation, a real owned blocked category, actual ordinary-clip channel URI/AudioAttributes and a required-reading veto after real channel preparation. Every posted notice uses a silent channel. Ordinary synthetic sound is read through the installed provider without playback. Imported tone bytes are deliberately distinct from shipped builtin hashes, so deleting an import cannot accidentally resolve a builtin fallback.

The provider cases inspect installed registration, exact MIME/metadata/normalized bytes, read-only descriptors, malformed URI/write rejection, silent versus nonzero PCM and isolation/deletion across two fresh owned scopes. A held unlinked read-only descriptor may finish; a later open of its deleted imported sound must fail. Self-UID ContentResolver access does not establish system-process URI access or a cross-UID grant.

The PendingIntent check proves canonical original identity/creator/immutability and the unchanged openIntent builder shape. It does not inspect hidden PendingIntent payload extras or send the Intent. The application coordinator is not rebound to these scoped stores, so the PendingIntents are never sent in this phase. Actual MainActivity dispatch requires the parent to adopt the matching owned Session/store and synthetic named reads before opening a valid scoped ticket; it is a separate integration scenario; no shared hook/entry DI overlay is required for these framework-only cases. These tests do not establish complete DEV, real Host/model flow, lockscreen rendering, launcher badge appearance, audible sound, background FCM/HMS delivery or vendor registration. Credentials/services are not provided, so remote push remains unverified.

## Exact cleanup

Framework APIs enumerate this package's notifications/channels; results are immediately filtered by the fixture's UUID tag/ID prefix before inspecting or recording their other fields. Cleanup cancels only those notifications and their observed owned PendingIntents, deletes only those channels, retires indexed fixture imports and removes only known records from that exact encrypted namespace. The default store, other channels/notices, other app data and the protected EasyWork package are untouched. Cleanup is attempted for every owned scope even if one fails. Denied-cycle data stays until its named grant phase; failures and unrecognized private files stay for diagnosis with a run/lease proof instead of forced deletion. No broad cancelAll, directory replacement or unknown-operation replay is used.

F52/F53, UI11 and S15/S16 changes are supplied in [native-system-parity-delta.json](native-system-parity-delta.json) for the parent-owned product/design/acceptance tables. iOS evidence remains independent; A6 remains paused. All five shared Session/Activity hooks are unchanged.
