## Implemented narrow path

`NativeChatNotificationCoordinator` owns the actual foreground monitor instances, settings/report mapping, explicit old-original query/off/gap actions and opaque-ticket queue. Its production factory receives the existing Session storage and required reading/reconcile/navigation port, and creates the sound library/platform with that same storage. It uses the shipping foreground delivery adapter; it does not wire the earlier standalone `NativeChatNotificationRuntime` into a second event path. There is no background service, vendor enrollment, conversation action or arbitrary method/REST forwarding.

All coordinator jobs run on Main; storage, large JSON, hashes and retained credentials run on IO. Cross-suspension checks use in-memory presentation/configuration fences and a volatile availability projection, without rereading Session UI state on IO. The caller invalidates before changes. Token/certificate/target/storage changes additionally stop captured-authority workers before mutation; navigation/read-surface changes invalidate presentation while preserving polling. A separate navigation lease keeps ordinary P7 visible-read publications from canceling a valid original-ticket lookup; real navigation/foreground/credential changes still invalidate it. Ordinary repeated workspace/history snapshots retain the same worker and polling interval. Worker identity uses authority plus chosen endpoint; online/name/account/reader metadata does not rotate authorization or restart it. A changed display name updates the next presentation without replacing the worker.

`NativeChatNotificationSavedConnection.capture` freezes the real saved client and credential together. Its credential epoch is SHA-256 over a fixed domain, complete account-independent Codex machine target, certificate fingerprint and credential hash. It survives process restart and ignores mutable in-memory revisions. Revisions are used only in the parent hook to reject a capture that raced a connection update. Workspace/history and notification requests use the captured credential/client, without a later live token callback.

Before the first monitor can attempt a write, the coordinator retains that complete authorization in the installation-local encrypted `native-chat-notification-authorizations-v1`. Original-ID query uses the exact saved authorization; it never substitutes a newer token or allocates an ID. The store is closed, versioned, bounded to 128 authorizations/1 MiB, preserves older entries and fails closed at capacity/unknown schema. It is not portable identity or an ordinary migration credential. The journal inventory keeps removed targets and pending originals visible even when realClients is empty; missing original authority remains an explicit recovery state. The read-only query port neither negotiates/registers nor processes a feed.

An untouched disabled installation creates neither notification identity, retained-authorization file, journal nor registration. The settings computer list can be populated from metadata only. Foreground processing waits for the actual P7 ledger to finish initialization; original-query actions and safe notification opening do not fabricate a ledger to bypass that gate.

`NativeChatNotificationSystem` is the narrow existing platform boundary. The production implementation continues to use NotificationManager/high-importance channels and native PendingIntent. The test implementation records a presentation and never emits a system notification. `NativeChatNotificationsPage`, `NativeChatNotificationSettingsEntry` and `NativeChatNotificationOpenStatus` supply the actual settings entry, page, per-target reports, original-query button and unavailable/retry status. Generic preference wakeups cannot invalidate a newly started explicit off callback. Language changes update native presentation text without restarting polling.

## Opaque Intent and original thread route

Only the exact notification action, canonical UUID ticket, matching application-owned URI/component and single ticket extra are accepted. Recognized malformed notification Intents must not fall through to pairing/deep links/attachment intake. Tickets queue while the Session is genuinely restoring or backgrounded, with bounded in-memory dedupe and persistent consumed-ticket protection. A newer tap supersedes an older pending lookup, whose late result cannot navigate or replace the newer status. Cold Activity restoration receives the same opaque original; it does not reconstruct a thread from extras.

On opening, the coordinator reads the still-current, unexpired receipt on IO, captures the current actually saved connection, and compares full target and stable credential epoch. Retained credentials from a removed connection are never a navigation fallback. The thread locator uses only named `HostReads.workspace` calls with that frozen connection, the shared bounded directory policy (1024 pages / 16384 unique threads, with cancellation and full-target checks), rejects a foreign/missing target and repeated cursor, and returns the actual thread object from the validated workspace. It never constructs a MobileThread, selects another owner, creates/unarchives a chat or sends input. Missing connection/thread/credential/TTL yields an unavailable state.

After the read, the presentation fence and local preference/lease are checked again inside the consuming storage transaction. The parent navigation port then synchronously installs the verified workspace and uses existing `selectVerifiedClient`/`selectThread`, preserving all original draft maps. A user navigation/background/credential change during the lookup cannot consume/open a stale route. A consumed ticket is never automatically replayed. Failed, unconsumed lookup can be retried explicitly with the same opaque ticket.

## Checks and acceptance split

The shipping Kotlin auxiliary runner now covers 71 cases, including the previous receipt/feed vectors, original-only recovery, read-only inventory, stable epoch/route distinctions, retained-authority capacity/schema/no-activation, and bounded actual-thread lookup. Its JVM memory/Looper/loopback ports are explicit auxiliary dependencies. The additional case compiles the very same native recovery transport fixture and calls it from a synthetic Main thread, then requires an applied original receipt and feed delivery; see [coordinator-native-fix.md](coordinator-native-fix.md). Existing 45 v1 wire/HTTP vectors are a separate regression. The runner exits nonzero on any fixture failure and bounds each compiler/JVM process to two minutes, so a failed assertion cannot leave the synthetic HTTP executor holding build JARs.

Twenty-one new `NativeChatNotificationCoordinatorTest` scenarios compile against real MainActivity, independent owned MobileSession and Keystore storage, required synthetic reading/Host ports and a system port that never notifies or requests permission. They cover actual entry/page/default-off, permission denial/new-event recovery, unchanged polling, original opaque presentation, atomic reading recheck, background/navigation callbacks, cold/warm/repeated/superseded/expired/wrong-authority/missing-thread tickets, old-query button, retained/missing authority and removed-connection inventory. Existing v2 fifteen storage/controller and four status-UI cases remain compiled.

The base workline does not own the Activity dispatcher. Its owned Activity Intent fixture explicitly calls `setIntent` then hands the stored Intent to the coordinator; it does not pretend that onCreate/onNewIntent hook integration has already occurred. Parent must apply the shared patch, bind the real Session port, and run actual dispatcher/Activity recreation with its device lease. This workline did not run any device/ADB, actual notification/permission dialog, actual Host subscription/model task, URI grant/playback/audible sound, vendor arrival or deployment. Those outcomes are separate acceptance rows, not inferred from compilation or the synthetic platform.
