# Active EasyWork ordinary-chat migration projection

This is a separately prepared Android projection candidate after the confirmed-receipt correction7570659f. It preserves ordinary client descriptions, draft/attachment state, history caches and immutable saved operations. It does not implement task/project management or establish full P7. The actual independent EasyWork runtime owners still require the separate close/join/callback work recorded in easywork-live-owner-intake.json; live export/DEV must not be declared ready from these fixture results.

## Typed source, inactive destination

A raw source client must have the actual canonical EasyWork full-target ID, account authority/subject, desktop/workspace/runtime, a strict AgentConnection and its exact credential in the source original-installation inventory. The original typed client JSON is captured and hashed in migration-easywork-business-v1, linked to the exact private-original installation/archive/name/digest. This is a typed descriptor snapshot, not a claim to preserve the original metadata substring's JSON whitespace or field order. Immutable intent/result strings and private original records remain exact.

The projected live client has no agentConnection, codexDirect or storageIdentity. Its versioned migrationEasyWork state carries only full target, original archive ID, path preference and candidate origins; requiresPairing=true and credentialState=none are fixed. It cannot carry a credential reference, pin, private key, grant, token or OIDC state. The original connection's reference and pin remain only in encrypted audit material. The client is offline and never marked reconnecting or authorized from cached runtime/capability fields.

AgentRegistry, the direct EasyWork adapter, the transport session and new journal preparation reject this state before resolving any provider/channel or submitting an operation. Pure provider title/permission descriptions remain available for rendering. Session refresh/history/events/network recovery and original receipt observers do not auto-query imported clients. Local cached chat search remains available; complete remote history needs pairing. The composer keeps local text editable while sending/control actions remain disabled. The chat caption and existing connection editor explain pairing instead of implying an automatic reconnect.

Current metadata alone may select a prior credential during explicit pairing. A guessed agent-$id name or an imported descriptor cannot promote an orphan. Existing per-action credential references and metadata commit authority remain intact. A newly verified explicit Desktop pairing constructs a normal client without the import state; its completed connection can replace only the same full target. The original imported operation rows remain migrationReadOnly even after pairing. No old unknown, ready or prepared input is automatically retried.

## Closed graph and limits

Catalog v1: at most256 original descriptors,256KiB UTF8 per original client and2MiB aggregate catalog. The existing128 active clients,1024 output records,8MiB individual text and192MiB combined framed archive limits still apply. Catalog size is checked incrementally before serializing an oversized aggregate. Mutable metadata parsing ends before the result graph is validated.

Catalog hashes, typed original fields, exact installation credential references and binding targets are checked. Full EasyWork account/runtime storage keys and workspace/history/operation targets cannot borrow Codex account-insensitive alias rules. User label/current path preference can change without rewriting the original descriptor; re-export preserves the original audit and private archive. Destination audit catalogs also merge without borrowing a missing source credential. Historical non-counting reading rows remain exact in the device audit; active reader scopes and pending acknowledgements do not migrate.

Versioned structural Schema and common fragment vectors are in easywork-business-v1.schema.json and easywork-business-v1-vectors.json. Native validation additionally checks UTF8 byte quotas, canonical hashes, port/origin semantics, original descriptor schema and complete graph relationships. Structural success cannot establish active authority or a complete migration.
