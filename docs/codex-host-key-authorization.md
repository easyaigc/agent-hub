# Codex 首次连接的 Host Key 授权

日期：2026-10-23。范围：F03／F57、iOS／Android 的 Codex 发现连接、Host 私网授权接口及接入 SKILL。

## 实现

自动发现只提供电脑候选，首次点选立即显示所选电脑与安全密钥表单。空值不能提交，取消和切换连接方式清空输入；错误 Key 不保存连接、不覆盖原凭据或草稿。正确 Host Key 通过 HTTPS 的 Authorization 头完成一次授权，手机保存加密交付的独立设备凭据，后续正常重连。已配对电脑重新授权前仍核对原证书和目标。

Host 的公开描述声明 `host-key`；旧 `automatic` 描述仍可解析，但新版手机拒绝走旧免密 claim。Host 同时拒绝缺失／错误 Key，以及使用设备凭据为其他设备授权。历史免密绑定缺少 `hostKeyAuthorized` 时不再通过鉴权，输入一次正确 Host Key 后沿用原设备凭据；原手动／二维码 Host Key 连接及新版已授权绑定继续有效。撤销、完整机器目标、证书校验和未知操作不重放的约束保留。

二维码包含密钥，属于显式凭据交付；EasyWork 继续使用自己的设备绑定授权流程。更新 Host 与手机 App 时须同时核对新授权流程，不能只改公开声明或 SKILL 文案。

## 继续排查与保留升级

正式 App 实际为 build 104。本次先将已部署程序的双通道、原桌面共享运行时、历史阅读与报告预览差异逐文件三方合回主仓库，保留已有未提交工作，没有整目录覆盖。合并后的完整 `pnpm check`、`pnpm build:ios` 和实际 Swift／Foundation 授权边界检查通过；旧 Android 和模拟器模型结果仍绑定先前指纹，不能自动升级为合并后或实体手机的通过证据。

本机已私有备份正式 App 数据容器和通知共享容器，并记录文件摘要。完整分发保留当前 Task Hub 的原冻结载荷，重新按原 manifest 恢复符号链接并验证相同 payload SHA-256，不变更运行中的 Task Hub。README 演示媒体不进入可复用接入包。

真机续验分别尝试取消测试检查器、明确 arm64 目标、命令行与 Xcode 图形界面；仍在 Runner 与 IDE 握手前退出 code 74，没有执行测试方法或提交模型任务。Mac 与 Runner 双侧 DTX 日志单独保留，开发者镜像可用且与 Xcode 匹配；这些证据尚不能确认拒绝来自哪一组件。独立 build 105 可由 CoreDevice 安装、启动及截图核对，并实际显示首次本地网络授权。原生用例补充仅处理本 App 的该授权提示，不放宽 Host Key、证书或目标检查。

用户已允许独立 App 的本地网络权限，并明确授权一次临时断开 Tailscale 的 Wi-Fi 对照。实际断开约 24 秒，原生测试仍在方法执行前退出 code 74；`finally` 与独立看护均负责恢复，最终状态为 Connected。清除单次子进程的代理环境变量后结果相同，没有改变系统代理。通过 CoreDevice 重启手机测试管理服务后核对到新进程，再次测试仍失败；没有重启手机、重配对或修改正式 App 数据。

补采的手机侧日志确认 IDE 已连接 testmanagerd，harness 与 Runner 会话标识匹配，并发起 serialized transport handoff。结合 Mac 与 Runner 日志，只能将失败范围缩小至交接后的代理通道建立阶段，不能将正常的 harness 交接关闭本身认定为根因，也不能确认 VPN、代理或某一 Apple 组件负责。原始手机日志仅保存在本机私有目录。

用户随后明确授权临时关闭 Hiddify 系统代理。本次只关闭 Wi-Fi 服务原有 HTTP／HTTPS／SOCKS 代理并清除测试子进程的代理环境变量，实际约 25 秒；原生测试仍在方法执行前退出 code 74。独立看护设置 60 秒恢复上限，测试结束由 `finally` 立即恢复，三项代理完整配置逐项读回与测试前相同，Tailscale 仍为 Connected。

不含产品源码、Host、业务依赖和模型请求的独立最小 SwiftUI／XCTest 样例也在首个方法前以相同 code 74 退出。随后只恢复本机当前用户的 CoreDeviceService，核对新进程、原配对与 Wi-Fi 隧道连接，再跑最小样例，结果相同；没有停止 root 服务、其他用户服务或模拟器。Xcode 首次启动组件检查正常，Mac 应用防火墙实际为关闭。这些结果证明失败可脱离产品代码复现，仍不能确认具体组件或固定修复方法。

CLI 的完整诊断要求 macOS 管理员认证，已取消；改用 Xcode Device Hub 的准确设备菜单“Collect sysdiagnose…”成功取得本机私有归档，核对 SHA-256 后仅解出系统日志与相关网络策略进行分析。两次最小样例的同一 Runner 连接在 serialized handoff 后约 1.2ms 即被手机内核以 `NECP` 为由丢弃，随后重传仍被丢弃，最终才退出 code 74。最初网络隐私配置显示独立 App 已允许、两个独立 XCTest Runner 仍为 `DenyMulticast: true`。用户通过同签名身份的独立权限准备程序允许后，重新安装原 Runner 的策略已明确保留允许，本地网络与无线数据均已开放，但原 Runner 仍退出 74；因此单独允许权限不能写成完整修复。

随后核对到多个不同 bundle 的 Xcode Runner 复用了同一个主程序 UUID；[Apple TN3178](https://developer.apple.com/documentation/technotes/tn3178-checking-for-and-resolving-build-uuid-problems) 说明网络子系统可能因该冲突对一个 App 套用另一 App 的限制。验收脚本现在只为已核对的独立物理 Runner 创建副本，按 bundle 生成稳定的唯一 UUID，用原开发证书重签并严格核对相同 entitlement，原 Runner、测试 App 及测试正文保持。薄 Mach-O、fat／fat64、跨 bundle 隔离及畸形输入边界检查通过；未修改系统策略、VPN 或代理。该副本连续恢复 XCTest 方法执行，最终完整授权场景通过。权限准备程序已被实际 XCTest Runner 替换，未作为验收替身。

后续原生失败发生在发消息前：实际输入框完整可见，但 XCTest 返回的键盘位于屏幕外。测试器现接受没有屏幕键盘的有效输入状态，仍要求输入框可点击、在 App 内且不被屏幕键盘覆盖；发送前另核对完整正文，保留原失败截图与几何证据。修复后的真实用例只提交一个输入，独立原 owner、模型回复、两个授权请求和恢复断言共同通过。此次只修复测试基础设施，未新增 Android／Windows 验收。

最终完整 `pnpm check` 通过后，从冻结源码的六个空编译目录按依赖顺序重新构建，并核对接入包源码、运行依赖闭包和 Task Hub 原载荷。统一包 SHA-256：`8d2c70b6c7ffdf71cfbe436cce9764c9f82e8bfccd41c8bc7422248569c7cbcb`。正式 Host 的新进程、服务入口和 ESM 解析指纹匹配该包；回环与原证书 HTTPS 读取返回 200，公开描述为 `host-key`，正式接口拒绝无／错误 Key 且未改变授权记录。首次切换遇到 launchd 尚未完成卸载，原服务恢复后，等待确认卸载完成再切换成功。
