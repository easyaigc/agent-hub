# 全局设计规范：版本演进与兼容

本规范适用于 Host、Adapter、手机与桌面客户端、应用协议、存储及升级部署。它是持续适用的设计与交付原则，不是某次版本修复的通过记录；各功能的实现、支持组合和实际验收仍按对应台账登记。

## 升级默认保持已有功能可用

每次升级先评估对既有版本、数据和使用流程的影响，默认提供向后兼容：新实现继续支持已有契约及已部署的旧端。在共同契约仍成立时，也应容忍可识别的新版本及新增可选字段，不仅因版本数字、构建号或目录元数据变化而拒绝连接、撤销能力或让已有功能突然失效。

Host、上游桌面和手机不必同步升级。新增能力独立协商，旧端未提供新能力时保留原有可用流程；只有确实依赖新能力的入口才提示限制。兼容范围以能力、数据结构与语义验证为依据，分别记录已验证版本和未验证组合，不承诺无法验证的任意未来版本，也不将历史通过直接升级为本次通过。

## 在适配边界处理差异

上游 wire、字段别名、默认值及旧格式转换留在适配层，公共领域与业务界面保持稳定。新增字段优先设计为可选且有明确缺省语义；读取响应时保留能够安全保留的未知字段，未知展示值可显示为未知，不能据此猜测执行语义。状态流版本、命令方法版本与持久化格式版本分别处理；增量必须绑定对应完整基线，不能将跨版本 patches 应用到旧结构上。

兼容读取不放宽命令输入契约、目标身份、证书、设备凭据或权限校验；没有共同语义的执行方法不能自动探测、替换或试发。新增字段容忍度不能变成任意方法、路径或参数透传。

## 保留数据与已提交意图

升级和迁移保留原身份、配置、草稿、附件、原操作 ID、不可变提交内容及回执。需要转换存储格式时，先核对原版本并提供可恢复迁移，不能把识别失败当成空数据覆盖，也不能依靠清数据、重新登录或更换身份恢复兼容。

结果未知时先查同一操作和准确目标的实际状态；兼容修复、重启、切换通道或超时均不构成自动重放输入的依据。明确连接错误应在有界时间内结束当前等待并保留恢复入口，不让界面一直停在“正在连接”；未确认的执行状态显示未知，已保存历史可读不代表实时 owner 可控。兼容问题只影响确实依赖该契约的能力，其他可用功能继续工作。

## 允许例外，但不能静默破坏

只有新旧设计或语义确实冲突，或兼容实现存在经分析难以合理承担的复杂度、维护成本或正确性问题时，才可以采用不兼容变更。版本号改变、尚未实现适配或只验证了新版本，都不能单独作为放弃兼容的理由。

不兼容变更须在设计与发布记录中明确：受影响版本和功能、具体冲突、已评估的兼容方案及不采用原因、用户影响、迁移步骤、数据保护与回退条件。按原任务授权和发布流程推进，在切换前说明影响；不能发布后才让用户通过功能失效发现变化。无法继续支持的能力给出具体原因和恢复路径，不影响无关能力，也不伪装为连接中或已成功。

## 每次升级的回归要求

按影响范围建立旧／新组合与升级恢复检查：新 Host 对既有桌面和手机、新手机对旧 Host、已识别的上游新状态结构，以及旧存储和在途操作的恢复。复用与当前指纹匹配的有效证据，变化的边界重新验证；不要求为无关改动制造新的模型输入。

涉及会话链路的升级，回归至少覆盖新建、已有会话发送、运行与完成的实时同步、断线或明确错误后的恢复，以及原草稿、附件和操作 ID 保留。独立核对每条已授权输入只提交一次，晚到结果不覆盖新草稿，错误等待有界；涉及真实桌面、模型或原生界面的断言，按项目现有环境与验收规则取得相应证据。辅助夹具、旧版本通过、部署成功和当前真实功能通过分别记录，不能相互替代。

本原则要求今后的设计、升级和交付执行上述检查；不能仅因规范已写入，就宣称所有历史版本或平台已经兼容、部署或验收通过。
