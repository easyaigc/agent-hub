本轮延续[长历史续修](history-thermal-20261024.md)，重点核对联网静置、真实混合交互中的读取、写入、CPU 和渲染开销。前后两份独立真机版本已完成相同静置和混合交互；以下分别记录指标、验证读取代价与限制。

本轮状态IO阶段的物理结果：会话逻辑写入下降65.7%，只读滚动hitch ratio均值约6.00→1.51ms/s；混合CPU33.85%→34.05%，独立静置CPU14.08%→14.50%，没有CPU下降证据，两轮混合最高热状态均为2。剩余CPU继续按调用栈定位，不能将本阶段写入收益描述成发热已解决。验收限定冻结源码与二进制，后续共享工作区的附件功能改动未纳入此通过指纹。

## 30% CPU 怎样判断

本项目的 CPU 百分比是进程所有线程的用户态和内核态 CPU 秒数之和除以实际秒数，再乘 100。30% 表示每秒约消耗 0.3 CPU 秒，是单核心时间的等价值。它没有直接给出整机算力占比、功耗或电池耗电比例。

“聊天 App 应低于多少 CPU”没有可直接套用的统一门槛。本轮没有同一手机、相同系统、消息内容、滚动和回复负载的竞品对照，不能给微信、ChatGPT 或其他 App 编造数字。Apple 的方法是按预期功能与实际使用情况确定需要改善的指标，再在同设备做前后测量；部分 Xcode 指标会提供相似 App 的目标建议，但这不等于统一的 CPU 合格线。参考 [Apple 性能改进流程](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance/)和 [Xcode 26 同类目标说明](https://developer.apple.com/videos/play/wwdc2025/247/)。

本轮增加保持真实网络和历史界面的 60 秒无操作窗口，单列静置 CPU、读写和编码开销。混合流程仍包含三客户端、两条专用本机新对话、三次真实输入、17 个具名步骤和 22 次滚动。XCTest 的可访问性查询也会给 App 增加工作，因此交互数据用于相同协议前后比较，不能直接充当普通用户日常平均占用。

渲染有独立参考：Apple 建议 hitch time ratio 尽量接近零，低于 5ms/s 通常良好，5～10ms/s 需要调查，超过 10ms/s 应优先处理。该指标统计错过渲染期限的时间；本项目的 CADisplayLink 移动帧间隔与“超过 50ms 帧数”是其他指标，不能混称。真机采用系统自然刷新策略，ProMotion或系统调度变化会影响帧间隔，不能将间隔直接当作业务代码执行时间。见 [Apple 渲染指标说明](https://developer.apple.com/videos/play/tech-talks/10855/)。

## 本次处理的写入放大

上轮混合流程的会话逻辑写入约 2.58MB/s，严格滚动约 0.81MB/s。iOS 每次状态保存都会重新编码和验证状态，并将旧备份写入 previous、上一次有效状态写入 backup，再原子写入新主文件。状态里还有多个客户端的目录和恢复信息，因此少量变化也会放大为三份完整数据写入。

新实现优先使用 APFS 的写时复制克隆。每个克隆都放入唯一私有暂存文件，校验内容并设置文件保护后，再原子发布；旧主文件和已知有效代次保持。文件系统不支持克隆或克隆内容不符时，沿用原有经过验证的字节写入。状态格式、加密策略、恢复选择、命令提交前持久化和未知操作查询规则保持。

这是 iOS 存储实现的专属问题。Android 使用 `AtomicFile`，没有相同的两代备份全量字节复制；本轮没有新增 Android 生产改动，前一轮双端缓存、富文本和隐藏动画修复继续保留，不能据此新增 Android 真机功耗结论。Apple 同样建议减少重复整文件写入，并说明原子文件发布还有文件系统元数据成本，见[减少磁盘写入](https://developer.apple.com/documentation/xcode/reducing-disk-writes)。

## 已完成的辅助验证
