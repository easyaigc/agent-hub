# Bounded Android text frames

The Android file archive now writes payload v4 inside the existing portable v2 encrypted envelope. Its bounded strict header contains text and binary descriptors only. Exact UTF-8 text frames precede binary frames, each group sorted by logical name. Every descriptor binds byte length, SHA-256 and the first up to44 bytes; framing reconstruction, whole-source receipt digest, authenticated envelope order and final EOF remain mandatory. Text/binary names are disjoint. A text record stays bounded at8MiB, the combined raw quota is192MiB and the existing1024-record limit remains. The legacy inline archive retains its8MiB cap; v1/v2/v3 archive and candidate reading remain available. This is an Android candidate format, without an iOS interoperability claim.

Source discovery decrypts one exact settled original at a time and retains its authenticated file/name/size/digest reader. The sparse text map decodes only a requested value. Archive aliases and destination merges retain descriptor references and small catalog changes. Closed graph parsing validates each record and retains shape/name and required identity/reference summaries; it no longer retains all JSON objects or all SavedOperation payloads. Original notification records use their independent frozen readers rather than a second generic JSON tree. The v2 reader returns a small validated installation/reference summary before authority decoding. No active original identity is imported and no unknown operation is reissued.

Candidate v4 uses the original candidate-v1 slot and receipt protocol. Text and binary frames stage as immutable encrypted cells under one random generation. Strict UTF-8, closed schemas, exact original aliases, complete graph and actual sound bytes validate before the sole slot publication. Identical-ID input is fully authenticated and checked against the original result, then its temporary cells are removed; it cannot restage an unknown result. Candidate slot and frame readers reject pending .bak/.new files without AtomicFile recovery. Legacy candidates and explicit cross-format replacement use the same boundary.

During activation, changed metadata, operation and device records are written one at a time to encrypted scratch cells under the existing candidate child. Unchanged originals stay references. Publication reads one text at a time and writes independent existing-format3 root records; no scratch pointer or portable authority enters the active generation. Only this attempt's named scratch cells are removed after publication/copy stops, including failed/unknown acknowledgements; the original candidate is preserved. Existing generation, quiescence lease, new Session restore, P8 credential leases and P9 cold ownership hooks remain unchanged.

Auxiliary validation: combined App/runner compilation and a JVM17 probe with actual text-map/framing/file-envelope/KDF source pass. The probe processes62,400,000 bytes across16 text records under a50,331,648-byte heap, tests sparse aliases/UTF-8, rejects malformed UTF-8/digest/quota faults and four invalid encrypted envelopes. Header JSON uses an org.json host parser and ASCII-password ICU uses JDK BreakIterator; native graph/Keystore execution is not inferred.

Four new native methods compile: near-maximum P9 v1/v2 originals plus authority exceed8MiB while independent real producer decoders remain prerequisites; cold candidate/current receipt and activation retain exact raw digests/source ciphertext/scratch cleanup; authenticated invalid UTF-8/duplicate JSON/reordered/future frames and pending slots/chunks preserve the original candidate; legacy/v3 explicit replacement and lazy/quota boundaries remain checked.
