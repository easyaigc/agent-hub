# 保持官方启动方式的原桌面创建入口研究

日期：2026-10-08。状态：正常启动下的控制聊天创建与主动打开入口已接入 iOS，八个真实专项场景逐项通过并独立复核，正式能力按当前构建/代码记录启用。早期一次性 PoC 与后续产品接入分开记录；失败批次与复测结果见 本机验收（本地文件 `docs/acceptance/ios-local.md`）。

## 2026-10-09 生命周期故障修正

历史八项通过只证明相应创建／打开行为。实际 Windows 与 Mac 的控制聊天被归档后，其 owner 消失，新建失效；该实现依赖普通聊天的生命周期，未满足产品要求。将其重新打开是临时恢复，不是根治。产品要求独立桥接服务，各目标仅安装、启动和验收；禁止用反归档、锁住聊天或远端修复提示词替代服务设计。

本次重新核对官方 [App Server](https://learn.chatgpt.com/docs/app-server)、[深链接](https://learn.chatgpt.com/docs/app/commands) 和 [Remote](https://learn.chatgpt.com/docs/remote-connections)。公开 `thread/start` 创建并订阅调用实例中的运行时；不能把另一个 reader 的创建当成原桌面创建。当前文档明确 paginated 新建不支持。新聊天深链接只导航／预填，未提供提交回执。本产品仍缺经验证的独立原桌面创建入口；未调用受保护工具管道、未伪造上下文、未启动重复执行实例。

后续隔离研究验证了官方 API 在零模型 Turn 下持久化空会话，并在准备进程退出后保留准确项目与 ID，三台电脑均通过。候选方案将空会话准备和原桌面独占执行分开；它调整原创建边界，尚待用户确认及真实 owner 接管验收，未启用。见 [空会话准备与原桌面独占执行研究](desktop-empty-thread-handoff.md)。

## 产品约束

- 用户从官方图标、Dock、Spotlight 等正常打开原桌面，行为保持不变。
- 不使用自定义 CLI 启动代理，不替换官方执行进程，不修改安装包或历史文件。
- 手机新建必须由原桌面执行，Host 独立托管创建不符合要求。
- 实际 Thread ID、项目归属、首条输入与原 owner 控制分别验证；历史读取不能证明原运行时连接。

此前 stdio 原型因改变启动链路而被排除。准备与启动脚本已经停用，旧本机 `launch.command` 也会收到拒绝。本次仅更新本产品 Host 的 owner 接入，官方桌面与 iOS 启动方式保持原样。

## 新发现：原桌面 App Tools 管道

本机构建 `26.1002.52244` 在正常启动时建立原生工具管道，地址由 `CODEX_APP_TOOLS_PIPE_PATH` 传给原执行环境。协议包含 `tools/list`、`tools/call` 和取消操作；内置创建工具最终交给原桌面 renderer 的实现，理论上避免独立执行服务。

但这不是任意同用户程序都能调用的公共 API。安装包只读检查发现 macOS socket peer 校验，涉及签名与可信进程来源。内置 MCP 服务还要求 executor 提供真实 thread / turn / tool-call 上下文；不能伪造这些身份当成 APP 已接入。

本轮已用 launchd 启动一个普通 Node 探针，父进程为 launchd，代表独立 Host 而非桌面中的 agent。它只发送一次 `tools/list`，不创建、不发送对话、不获取凭据。原桌面正在监听该 socket，但探针未收到工具列表；桌面日志记录 `dynamic_app_tools_peer_rejected reason=untrusted-process-ancestry`。探针任务已清理，没有尝试伪造签名、祖先进程、会话元数据或关闭校验。该路径不能宣称普通 Host 可用。

普通 MCP 插件是官方支持的扩展方式，但不因此获得反向调用所有内置工具的授权。[官方 MCP 文档](https://learn.chatgpt.com/docs/extend/mcp) 说明了 stdio / HTTP 服务器与插件配置；不能把它当作独立 Host 的 App Tools 调用许可。若探索扩展路线，必须用真实已注册的调用上下文、保持授权检查，单独验收其生命周期和允许的操作。

## 已验证的有限路线：原桌面控制聊天

目标链路为：手机显式创建请求 → Host 校验 / 记录 intent → 原桌面专用控制聊天 → 原桌面内置 `create_thread` → 返回实际 Thread ID → 原 owner 控制链路。新用户聊天仍由原桌面创建；Host 不启动第二个执行器，官方启动方式保持原样。

这是原桌面中的控制聊天，区别于 Host 托管执行。它会增加一个用户可见的辅助聊天，并有模型调度开销、忙碌排队和运行生命周期成本。用户回复“允许，验证”后，本轮新增一个控制聊天与一条验收聊天，没有建立循环、自动化或长期控制授权。

实际流程是：使用原桌面内置工具在已保存的 local 项目建立控制聊天，只回复就绪码；Host 通过真实 owner 接入，然后使用 APP 已有的 `POST /v1/replies` 向该控制聊天发送唯一一次创建请求；控制聊天核对项目后，调用一次原桌面 `create_thread`，新聊天回复随机校验码并结束。没有使用 worktree/cloud，没有修改项目文件、历史文件或官方启动方式。

### 列表遗漏的接入修复

本机构建中，这两条 `agent_created_thread` 聊天在真实持久记录与原 owner 中存在，但 metadata reader 的 `thread/list` 未返回它们。RuntimeSession 现在允许显式打开一个列表中尚未登记的 Thread ID，前提是 IPC 已验证匹配 ID / local 的 owner 快照且 owner 仍有效；只登记在本产品缓存中。项目仍按根目录精确匹配展示，未加载或无法确认 owner 的未知目标保持拒绝。

新增 IPC/session fixture 使用实际本地 socket 与只读 reader 子进程，验证列表隐藏的聊天可在 owner 确认后接入、并发打开只跟随一次、未知无 owner 目标拒绝，以及 Host/项目绑定。这是边界测试；上表是独立的真实桌面证据。

该路线还需解决控制聊天在桌面重启后的加载、空闲时的请求唤醒、精确正文传递、双击/超时/断网不重放等问题。内置工具的新建参数目前是 prompt，首条原生图像/文件是否可覆盖仍需另验；不能把路径写入 prompt 等同于原生上传通过。无项目、空项目、停止和审批也仍按产品六项门槛验收。

## iOS 接入实现

`DesktopControllerBridge` 使用已有原桌面 owner，控制聊天只承担每次创建或打开请求。Host 无法直接调用受保护的 App Tools 管道，也没有伪造工具调用身份；由原桌面真实模型 Turn 使用已注册工具，工具权限与官方启动方式保留。未使用已被访问限制拒绝的桌面 UI 自动化通道。

创建分为三个有明确回执的阶段：

1. iOS 保存不可变操作 ID、项目、正文和附件摘要；Host 暂存并校验原始字节。
2. 原控制聊天先用 `list_projects` 取得真实本地目录及 App 项目 ID，再调用一次 `create_thread`。Host 核对实际 `mcpToolCall` 参数与工具返回，拒绝把助手文字或最新列表条目当成结果。无项目使用显式 projectless target。
3. 新聊天先完成“会话已就绪”的初始化轮，Host 确认原 owner / cwd 或 projectless 状态，再通过已有 IPC 提交用户的原始文字、原生 localImage 和受控文件路径。首条消息固定使用 `first-<operation-id>` 去重，提交一次后才确认创建。

原工具要求非空 prompt，因此原桌面保留一个实际初始化 Turn，随后才是首条原生 userMessage；这不是零 Turn 空线程。手机进入真实聊天后隐藏本产品明确标记的初始化轮，保留用户请求与真实输出，不编辑原历史。未发送的新聊天仍是手机草稿，不向桌面提交占位消息。

项目内和空项目使用实际保存项目；多个 workspace 根目录依据内置项目目录精确匹配主目录，不能直接混用 App 项目 ID 与 App Server 项目 ID。当前官方 project_id 可能仍为空，Host 仅保存本产品的显示归属，不写回官方元数据。桌面标题以实时 owner 的标题为准。

打开已知未加载聊天时，iOS 提交绑定 Host/Thread/操作 ID 的打开请求，控制聊天调用原内置 `navigate_to_codex_page`，Host 只在目标原 owner 可用后返回 opened。打开不向目标发送占位消息。后续正文、流式进度、停止与审批继续走该目标原 owner。并发打开同一聊天共享一次打开动作，旧 iOS 请求不能覆盖新选择。

创建 journal 在调用前落盘 sent，真实结果 ID 在首条输入前保存；超时与 Host 重启查询同一控制 Turn / 已保存结果，不再调用创建。若结果仍不明确则保持 outcome-unknown。控制操作串行，图片没有仅转成控制提示词中的文件名。

## 可用条件

Host 本地配置固定 Host ID、控制 Thread ID 与已验证桌面版本。`validationOnly=true` 仅开放测试能力；普通 App 不使用测试能力。正式启用还要求 real-desktop-controller 记录、Adapter 摘要、六项创建门槛和未加载打开实际通过，缺证据或 owner 时关闭能力。真实验收与 fixture 分开。

这条路径增加一个用户可见的控制聊天及模型调度开销，创建需要等待两段真实 Turn。控制聊天必须处于原桌面已加载状态；桌面冷启动后自动恢复控制聊天尚未验证，必要时需用户在正常启动的原桌面打开它。Host 不修改启动参数、登录凭据或安装包。不承诺所有版本、锁屏或后台场景可用。
