# Codex control request deadline regression

The fixtures use synthetic hosts and do not access Codex, a model, or production state. Keep their generated tokens and metadata in a task-owned private directory and stop all task-created services after testing. Never put production credentials or device identifiers in the repository.

From the repository root, run the synthetic protocol checks:

```sh
node scripts/fixtures/codex-control-deadline/inflight-open-fixture-selftest.mjs
node scripts/fixtures/codex-control-deadline/reply-fixture-selftest.mjs
```

For a simulator, start `inflight-open-fixture.mjs` with `INFLIGHT_PHASE=fixed` and optional `INFLIGHT_PORT` (default 18802). Set the XCTest runner environment `CODEX_FIXTURE_URL` to its loopback URL and run `testInFlightOpenBackgroundDeadlineAndSameIDRecovery`. Baseline mode is only for controlled reproduction using an old isolated build. For `testControlDeadlineSubmittedReplyRecovery`, start `reply-wait-fixture.mjs` with `REPLY_WAIT_AUTOMATIC=1 REPLY_WAIT_TRICKLE=1 REPLY_WAIT_PORT=18816` and set `CODEX_REPLY_FIXTURE_URL` to its loopback root.

For a physical device, set `CODEX_DEADLINE_OUTPUT` to a fresh private directory for each attempt and run `node scripts/fixtures/codex-control-deadline/physical-orchestrator.mjs open` or the same command with `reply` from the repository root. Existing metadata is never overwritten. It listens only on loopback by default, emits the controller PID, and writes synthetic metadata and results to that directory. The controller recovers the original open after five seconds or confirms the original reply after forty seconds; it independently verifies at least 500 trickle chunks, stream closure between 30 and 37.5 seconds, original-ID queries and exactly one submission. The physical controller selects the synthetic desktop-domain response; simulator defaults remain unchanged. Its result first has `phase=count-observed`, then `phase=ui-finished` after the parent confirms completion. It remains running after the count check: after the UI test exits, send SIGTERM to the verified controller PID so it can verify final counts and stop its own fixture.

The physical App requires HTTPS. Build the Host workspace first, then run `tls-fixture.mjs` separately with `CODEX_DEADLINE_BACKEND` set to the controller's loopback endpoint (`http://127.0.0.1:18812/` for open or port 18826 for reply), `CODEX_DEADLINE_FIXTURE_JSON` set to the controller's private metadata file, `FIXTURE_BIND` set to the test computer's device-reachable private IPv4 address, and `CODEX_DEADLINE_TLS_PORT`, `CODEX_DEADLINE_TLS_STATE` and `CODEX_DEADLINE_TLS_METADATA` set to a task-owned port, private state directory and new private metadata file. The wrapper creates its own certificate and uses the real discovery and certificate-pinning transport; it accepts only synthetic fixture identities. It does not start Codex. The returned metadata includes `pairingUri` and full target identity. Pass its complete JSON as `CODEX_PHYSICAL_OPEN_FIXTURE_JSON` or `CODEX_PHYSICAL_REPLY_FIXTURE_JSON` in the private XCTest runner configuration, alongside `HOST_KEY_DEV_APP_BUNDLE_ID` for the independent App. The Runner performs UI and timing checks without network access; the App itself reaches the fixture over pinned HTTPS.

The separately authorized real Host cases use `CODEX_REAL_FIXTURE_JSON` and `CODEX_FORMAL_FIXTURE_JSON` plus `CODEX_FORMAL_HOST_KEY` in a private runner configuration. They use exact Host discovery and the secure Host Key field, and require a task-owned chat, a single authorized submission, original-operation reconciliation on unknown outcomes and independent desktop-owner verification. Do not route real credentials through the synthetic TLS wrapper. The simulator-only real Host cases use their corresponding fixture URL variables. Set values in the XCTest runner configuration; the application launch environment and test runner environment are distinct.
