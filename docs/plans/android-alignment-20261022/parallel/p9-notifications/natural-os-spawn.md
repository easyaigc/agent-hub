# P9 natural OS process creation: review and minimum preparation

This design records the `5b9b402c` preparation checkpoint. The later [permit-store first implementation stage](natural-permit-store.md) moves its model into debug source and implements the authenticated durable store. Natural Activity/OS integration remains pending; the scope and implementation statements below describe the earlier checkpoint.

Status: the current hook cannot safely run this stronger scenario. This change prepares a strict permit reducer and acceptance design. It does **not** install a persistent permit, connect a new Activity path, implement an observer, or certify natural process creation. The original `8c648123` instrumented-reader OS three-role Spec remains unchanged and pending parent execution. The separately accepted worker correction and its 30 native methods do not certify either OS scenario.

## Reviewed boundary

Read-only review uses parent snapshot `cd3c9a127b126eaf988eb06cae6610ea616be441`. `NativeChatNotificationColdStart.kt` is `25a1a3f830dad3eae47175894b56666452328f45bffee3feb76934bc68d91049`. Its `prepareReader` places the original plan in a volatile, process-local `permit`. `selectForActivity` requires that value before constructing its fixture Session. A genuinely new OS-created process has no such value. Removing this check would let an armed or unknown router select storage without the accepted reader preflight, so this preparation preserves the rejection.

Parent MainActivity `27c5ad585cff9d0ac592b64691f9c235d31ae5038ddd8a4e974ad4e3616993e8` already calls that hook before its default Session/storage fallback. MobileSession `e9c38fe9e2d87f7df5e67f4534e1087f83a2440ec7c21e79554693a1977094d1` already supplies the bounded synthetic read ports. Neither shared file needs a change for the proposed initial selection. No base/proposed patch for either is delivered or applied here. A later completion observer must use a narrow acceptance-only callback after actual restore/open, and must be reviewed against then-current source rather than fabricating a Session callback.

Android documents that the system retains a [PendingIntent token after its creator process dies](https://developer.android.com/reference/android/app/PendingIntent). That permits a retained original token to be used by SystemUI; it is not evidence that a particular device retained a notification or created the intended process. Starting [instrumentation against the receiver](https://developer.android.com/guide/topics/manifest/instrumentation-element) would already start/run in that target process and would reduce the claim to the existing instrumented-reader boundary.

## Source prepared here

`scripts/mobile/fixtures/native/NativeChatNotificationNaturalPermit.kt` is a standalone acceptance candidate, outside Android production/test source sets. It has no Android caller and no file, key, network, notification or Activity effect. `proposeClaim` and `proposeComplete` produce state proposals; they confer no authority to open a store or execute an action. All trusted observations are required constructor arguments. The caller cannot inherit default positive permission/key/provenance checks.

The candidate uses version 1, at most 8 KiB, canonical UTF-8 with a fixed ordered `key=value\n` schema. Unknown/repeated/reordered keys, noncanonical numbers, malformed UTF-8, foreign package/target, inconsistent phase fields and trailing material are rejected. This avoids relying on Android and JVM JSON parsers accepting identical syntax. This is proposed **plaintext inside an authenticated encrypted record**, not a plaintext authorization file.

Immutable fields bind one canonical lease, attempt ID, original ticket, plan hash, normalized original receipt hash, original authority/token hash, derived full synthetic target, installed UID, exact single app/runner APK hashes, signer-set hash, device challenge hash, published OS marker hash, writer PID/nonce, boot count and wall/elapsed lifetime. Target values are fixed from the original lease; no directory, endpoint, method or business body can be supplied. Only the original successful case is eligible for a future arm operation. Hashes are correlations, not secret credentials.

The reducer accepts `armed → claimed → complete`. Claim requires exactly the same independently observed original/install tuple, existing device-key authentication and challenge, intact material, armed original router, published OS record, unconsumed original receipt and exact product Intent, current notification permission, one first Activity, no default selection/retained Session, a different process identity, unchanged boot, and bounded monotonic/wall time. `claimed` and `complete` never return to `armed`. Permission restoration does not make an attempted lease reusable. Completion requires the same consumer, original ticket/normalized receipt/full target, consumed receipt, one Activity, zero default selections and zero business/notification commands. Rejected proposals preserve the original state.

Run the auxiliary from the checkout with its private toolchain file and cached Kotlin dependencies:

```sh
GRADLE_USER_HOME=<existing-private-gradle-cache> \
  node scripts/mobile/check-chat-notification-natural-permit.mjs
```

The 64 checks cover strict decoding, changed original/install/key/OS bindings, permission denial, unknown/partial material, instrumented receiver, clock/boot boundaries, duplicate/late consumer rejection and exact completion. They compile/run the reducer on JVM 17. Device observations, KeyStore authentication, disk durability, process locking, permission SDK calls and natural OS creation are explicit unimplemented seams. These checks must not be entered as native or full DEV results.

## Minimum persistent adapter, still required

1. Add an acceptance-only **existing-key-only** store. `NativeSessionStorage` has a lazy key generator when its alias is missing, so using its normal fallback for this permit would violate the no-new-identity requirement. The adapter must obtain the existing installation AES key directly, never invoke KeyGenerator, never import a key and fail on absent/invalidated/locked key. A writer creates one random challenge, seals it with that same existing key and fixed domain/AAD, and binds the challenge digest to the immutable permit. The reader must actually authenticate/decrypt both the permit and original challenge with that key. A matching public hash or a caller's Boolean is not that proof. Failure preserves ciphertext and blocks storage selection.
2. Use a new fixed private acceptance namespace, proposed `P9-notification-natural-permit-v1`, with fixed record names and explicit no-follow file validation. Do not add a record or lock to the old router directory: its current guard intentionally accepts only its single exact marker. No namespace comes from Intent extras. Old, incomplete, unknown or other-lease material is inspection-only. No absence/parse/decrypt/sidecar failure may become a fallback to default storage when any latch material exists. A clean absence of both existing router and new latch preserves ordinary App startup.
3. Introduce mutual exclusion spanning processes and a write-ahead claim. NativeSessionStorage's lock is process-local; [AtomicFile provides replacement integrity without a cross-process lock](https://developer.android.com/reference/android/util/AtomicFile). The new adapter must hold a fixed lock while reading/authenticating the armed state, checking the exact original, writing the claimed state, syncing and reading it back. It must preserve the same attempt identity. No selected router, Session or default storage is opened before verified claim persistence. A lock timeout, failed write/readback, partial sidecar or unknown outcome stops. A committed claim with a missing selected-router result is unresolved, never rearmed. The lock/file policy and failure injection remain to be implemented and tested on Android.
4. Arm **only during the new writer's authorized run**, after one actual OS post has a matching own SDK row and its original `published` marker. Revalidate the original claimed receipt and all installed/key/permission bindings without altering them. Its deadline must be no later than the original cold plan/ticket expiry, using the same boot and remaining elapsed lifetime; do not start another full TTL when arming late. Generate only the fixture challenge/attempt, never another identity, event, ticket, receipt, registration or post. Do not append this permit to any old or unknown lease, including the pending instrumented-reader queue.
5. Extend the existing `selectForActivity` hook narrowly: use the old volatile permit for its existing instrumented path; otherwise require this exact persistent natural permit and successful durable claim. Preserve strict opaque Intent checks, old router validation and rejection of other launches. Record `selected` on the original router, then bind the existing fixture. Any failure after a durable claim leaves an unresolved attempt. A ticket match does not establish SystemUI as caller; only the independent OS evidence below establishes that provenance. Do not introduce an exported receiver/provider, arbitrary IPC, general launch override or new production routing behavior.
6. After actual restore and original coordinator open, the acceptance hook may emit a bounded, durable completion proof containing the current PID/nonce/boot/elapsed start, original scope/thread/draft hash, normalized original consumed receipt, exact operation counts, Activity/default-store counts, app/runner/signer/key bindings and the claim ID. It must not drive an open or synthesize completion. If incomplete, the parent inspects that attempt; it does not restart to replay it. An exact completed observer may later archive/release the one latch only after the original consumer is gone and every original proof matches; preserve encrypted fixture and failure evidence. A generic failed-latch cleanup is outside this design.

Pre-Activity here means before the first Activity selects its Session/storage, not that an Activity has never been instantiated. The existing hook executes after `super.onCreate`. A future candidate must independently audit Application/provider initialization for default-store or key-generation effects before that hook. Do not rename this checkpoint as an earlier Application guarantee.

## Native scheduling proposal: independent observer, no receiver reader startup

Use a new lease and independently fingerprinted candidate containing this reviewed adapter. Keep accepted worker source unchanged. Do not schedule this preparation against the old pending three-role OS lease or count any historical closed5/worker30 result toward it.

| Role                                          | Required evidence                                                                                                                                                                                                                                          | Stop condition                                                                                                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writer, receiver instrumentation, no Activity | Existing key; fresh lease; original plan/receipt/authority; exactly one production post; SDK-observed original immutable contentIntent/row; durable natural permit; zero default/commands                                                                  | Denial, unknown post/permit write or any old material; no repost/rearm                                                                                        |
| External observer, separate process and UID   | Installed receiver/runner/examiner fingerprints; exact receiver UID; receiver has no process before and immediately at the original SystemUI click; writer gone; one owned UUID row and one ACTION_CLICK; new OS-created receiver PID observed after click | Target instrumentation starts the receiver, any receiver process exists early, row missing/ambiguous/changed, rejected/unknown click; no launch/send fallback |
| Receiver created by OS, no instrumentation    | One durable permit claim and selected original router; actual Main/Session restores original thread/draft and consumes same original receipt; zero default and commands; durable completion                                                                | Any binding/permission/key mismatch, expiry, restore or observation failure; original latch/receipt retained                                                  |
| Post-exit observer/reconciliation             | Same consumer PID/nonce now gone; original encrypted values and completion proof; exact own row cleanup and permission/other-notification checks                                                                                                           | Unfinished claim or mismatched proof; no generic disarm, input, post or receipt repair                                                                        |

The external observer must instrument its own/examiner package, never the receiver. Existing examiner packaging is a possible source of a fixed separate UID, not an accepted implementation for this notification path. Verify actual targetPackage and installed UIDs; a `.test` name alone is insufficient. Its bounded read-only process observations must cover the exact UID/process set, include boot/start identity and distinguish PID reuse. It may use fixed native diagnostics under the parent's device policy, but no arbitrary shell/IPC arguments, package force-stop, clear, reinstall or process-creating receiver probe. The test does not cause process death. If the original notification fails to survive the writer's ordinary exit, record that blocker and stop.

Before clicking, externally persist the immutable click attempt and its last absent-process observation. Use the old Spec's bounded SystemUI ownership/UUID selector and own-row-only crop. Exactly one original row click is allowed. Never repair a missing row by posting, retrieving with `getActivity`, direct-starting Main, or calling PendingIntent.send as a first-open fallback. No model or Host connection is needed. A process seen before the click invalidates the natural-creation claim even if the Activity was not yet visible.

The independent UID cannot use NotificationManager.getActiveNotifications to fetch the receiver's private PendingIntent object. Correlate writer SDK proof, unchanged published marker/permit, exact own SystemUI row, receiver's strict ticket and normalized same receipt. If that proof chain cannot establish the original token on the device, fail the stronger token claim; do not invent a returned object. The old instrumented-reader case's retained-object SDK duplicate is a separate proof. Natural-spawn preparation does not create another token for duplicate testing or claim that Activity Intent data alone proves Binder-token identity.

Permission belongs to the parent's accepted-package before/restore policy. The writer requires declared/granted/enabled/canPost and the original channel state; the consumer rechecks current permission/channel against the sealed publication evidence. Denial/revocation is a refusal with no permission prompt or automatic recovery. No cancelAll, channel deletion or other notification access is introduced. Cleanup may cancel only the exact original tag/id after current original matching; failure/unknown completion retains the original evidence. Process creation, first Activity, SDK duplicate, receipt consumption and permission recovery are separate assertions.
