## 一套公共协议，两种适配实现

用户要求的“与 Codex Host 相同协议”落实为：**公共层只有一份版本化领域模型、具名操作、能力描述、错误/回执状态机和验收断言**。不新增 EasyWork 专属业务规则副本；Codex JSON-RPC 和 EasyWork v2/EWDAP/1 留在各自 Adapter/Transport 内。现有 HTTPS 与加密 WSS/Relay 可以不同，不能借统一协议删除 EasyWork 的 account/grant/DPoP 或套用 Codex Host Key。

| 边界         | 统一要求                                                                                            | 实现位置                                                                             |
| ------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 身份         | Agent、Host、workspace、runtime；所有会话操作再绑定 thread，控制绑定原 Turn/Run；路径不参与业务身份 | `packages/protocol`、KMP规则、各 Provider adapter；EasyWork account/绑定继续附加验证 |
| 能力         | 声明同时有真实 dispatcher、已装配服务、权限和就绪状态；支持版本和不支持原因明确                     | Host/桌面 capability builder，手机按共同 capability 投影；不以客户端名字决定业务     |
| 命令         | 白名单具名操作、严格参数，运行时执行权限只在 Host；禁止任意 IPC/shell/method 透传                   | Codex Host→Adapter；EasyWork RemoteCommandService→bridge→原桌面服务                  |
| 操作账本     | 稳定 operation ID + 原 target/method/params 指纹；提交前持久化；同ID同意图返回原回执、不同意图冲突  | Host/桌面持久回执；手机独立 outbox                                                   |
| 结果         | 命令处理完成、排队接受、模型结束分开；missing/超时不推断未写入；未知先查原ID                        | 共用领域阶段/错误，adapter归一化；不改原不可变意图                                   |
| 恢复         | 跨LAN/Relay复用原ID；结束等待只脱离UI，保留回执与附件；迟到结果不覆盖新草稿                         | 手机会话层与Host账本，传输层只处理重连/序号                                          |
| 数据与资源   | history可读不等于runtime可控；epoch/游标/分支修订防乱序；资源绑定原消息/源版本及授权                | adapter、公共Schema/向量、只读reader和资源服务                                       |
| 服务生命周期 | Host独立于安装/控制聊天；原桌面独占执行；创建准备器不得启动模型轮                                   | Host服务与EasyWork main持久服务；没有普通聊天driver依赖                              |

新增公共语义先在 `packages/protocol` 定义，形成严格Schema、跨语言向量和一份可分发的契约/manifest；EasyWork桌面消费同一版本或由受控适配层映射，禁止手抄另一套含不同错误语义的DTO。声明兼容范围后再接iOS和KMP。协议更新必须写 `docs/protocol.md`；实际架构/能力变化同步 `architecture.md`、`feasibility.md`，区分拟实现、实现、验证。

## 两项确定差距的设计细化

### EW09：大小上限与文件通道

1. 沿共同文件领域契约区分可选总文件上限与分块/消息预算。已有Codex `maxFileBytes: null` 表示未配置总量上限；EasyWork新版本映射相同领域语义。旧端缺版本/能力时沿其显式限制，不把缺字段猜成无限。
2. 桌面端审阅实际 `resource/upload*`、`download`、`transfer-list` 的配额、SQLite大小存储和offset类型；手机审阅prepare、回执、下载解析、流式落盘。发现桌面已有能力就接通，不再做重复实现。
3. 不将大文件塞到聊天或协调正文；使用独立文件通道的稳定transfer ID、路径、字节数和SHA-256。旧协议命名包含Base64不代表授权扩展正文承载；新增版本优先独立分块文件通道，严格保持既有总量/每帧安全预算。
4. 长文件磁盘/内存不足、变更原件、offset冲突、断线重启必须可查询；未知命令不重发，续传只能基于同一原transfer的权威偏移及已定义幂等契约。渲染预算与可下载/分享范围分开。

### EW10：文档内资源解析

沿当前候选 `AgentClient.resolveDocumentFile` 的领域语义设计；建议EasyWork具名方法为 `resource/resolve-document-link`，**此名字属于待定契约，不是已实现接口**。在EW01查最新桌面源码后优先复用等价现有方法；新增名称/版本必须先通过公共契约审阅。

输入绑定完整目标、thread、原资源/附件ID、文档源SHA-256和原链接；按原文实际存在的链接解析，禁止手机传任意磁盘路径获取文件。相对路径以原文件目录为基准；源文件变化、越界、符号链接逃逸、伪造引用和跨thread明确拒绝。结果投影成既有RemoteAttachment/逻辑资源，保留resource ID与版本ID分别表达身份和摘要，复用下载/预览/取消路径。外部网页仍走现有浏览器且不携带Host凭据。旧端明确“不支持/请更新”，不假成功。
