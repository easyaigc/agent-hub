# Desktop Trace 持续增长：根因与治理方案

日期：2026-11-23。状态：只读诊断与实施提案；尚未修改运行程序、正式配置或删除 Trace。源码基线为 `98841a6b62a28922ec234477eb19d7e3c2e6e744`，工作区已有其他任务改动，本报告不将其视为已发布版本。

## 结论与证据边界

现象来自三层叠加：诊断采集覆盖整个原 Codex 执行树；回收器错误地把 `rollout_ended` 当作必须位于文件末尾的封口；没有覆盖未封口、无法解析及活动写入的目录总量控制。修复单次扫描成本或清空旧目录均不能阻止复发。

用户截图显示另一个用户目录的 `desktop-trace/traces` 约 44.54 GB。截图目标机的准确身份、已加载模块、增长速率和分类尚未取得，不能用下面的本机数据代替该机验收，也不根据用户名或 audit 目录后缀猜测 Host 身份。

本机采用只读枚举、文件元数据、有限尾部读取及三个大 bundle 的结构统计；不输出聊天正文，不调用具有删除副作用的 `DesktopTraceRetention.process()`。必要明细保存在本机私有证据目录，仓库只记录脱敏聚合。

以上年龄只表示未写入的时间，不能证明无 writer 或可删除。已有结束记录也只证明当前第一道门禁误判，不能据此承诺上述字节均可立即回收。

本机运行进程的 observer、retention 两个开关均为 `1`，因此不是只缺少开启配置。实际安装的 retention 模块与当前源码均使用相同的末条门禁，且没有识别 `recording_completed`。最近落盘回收状态为 2026-11-19，记录 retired=0、releasedBytes=0、retained=55847、failed=33、pending=819；这是旧快照，不能当成本次实时运行结果。`retained` 是累计处理次数，不是不同文件数。Host 托管进程仍在运行，状态文件陈旧的具体运行原因尚未确定。

## 具体根因

### 1. 普通功能依赖的采集面过大

`scripts/desktop-suggestion-trace-environment.mjs` 通过登录环境设置 `CODEX_ROLLOUT_TRACE_ROOT`。代码明确说明这是 GUI 后代进程继承的环境变量，不是只针对一个 App 或聊天的设置。Host 的观察开关与原 Codex 的写入开关分属不同进程；停止观察或重启 Host 不能关闭已运行原进程中的记录器。

官方固定版本源码说明，每个独立 root session 创建一个 bundle，spawn 子线程共享它。Trace 可以包含提示、模型返回、工具输入输出及终端结果，它是诊断记录，不是建议文本缓存。参见 [固定版本 thread.rs](https://github.com/openai/codex/blob/rust-v0.163.0-alpha.10.2/codex-rs/rollout-trace/src/thread.rs#L35-L40) 与 [官方 Trace 说明](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md)。

本机最大 bundle 达 1.875 GB，包含 120 次 thread_started、13,707 次 inference_started、122,431 个 payload 文件。另一 bundle 的 111 份推理请求累计约 472.5 MB，而整个 bundle 约 511.6 MB；首、中、末三个请求仍有 12 个完全相同的 input item。该观测证明完整请求、部分重复上下文与高频工具记录会放大体量。部分 WebSocket 请求采用 `previous_response_id` 和增量 input，不能笼统声称每次请求均重复全历史，也不能据此推导所有场景都呈平方增长。

### 2. 将业务生命周期误当成记录器生命周期

`packages/codex-adapter/src/desktop-trace-retention.ts` 的 `finalEvent()` 只取最后一条 JSON；`process()` 要求这一条恰好是 `rollout_ended` 且状态 completed，否则立即返回 `active-or-unsealed`，后面的分类、持久保存与删除检查完全不会执行。

现场 Schema 2 的 553 个 bundle 均符合：前面已有同 schema、同 rollout 的 completed 事件，之后追加 `recording_completed`。它们会被现有门禁稳定拒绝。另有子线程、工具或取消收尾事件落在 rollout 结束之后的例子；固定版本上游也以共享 writer 承载子线程，root 结束并不禁止其他持有者继续追加。

当前官方 main 将 `RecordingCompleted` 定义为所有 producer 释放 writer 且无记录错误后的最终记录，关闭时先排空队列再封口；参见 [raw_event.rs](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/src/raw_event.rs#L72-L80) 与 [关闭流程](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md#L152-L169)。main 当前为 raw schema 3，不能冒充现场 Schema 2 对应二进制的精确实现证明；现场不匹配门禁本身已由本机文件独立证实。

所以既不能继续要求 rollout 是末条，也不能改成“历史中找到任意 rollout_ended 就允许删除”。需要区分业务结束、记录器完成、仍有 writer、异常遗留和格式不支持。

### 3. 未封口与未知状态没有完整退出路径

活动 session、子线程仍持有 writer、进程异常退出、记录失败、旧格式差异都可能缺少预期末条。当前把它们全部归为 `active-or-unsealed`，没有绑定 producer generation 的遗留对账流程。manifest 的现有字段不含可直接证明当前 writer 已退出的 PID/启动时间，不能只靠文件年龄补造这种证明。

其他长期保留条件包括来源无法验证、读取预算超限、预测无法提取、文件身份矛盾和未决回收操作。“24 小时保留”只适用于已经跨过封口与来源校验的部分已知失败/取消/空结果；不是全目录 TTL。超时删除所有未知数据会丢掉仍可能需要的唯一证据。

### 4. 有安全删除流程，没有全目录容量闭环

现有代码没有原始 Trace 总字节、总文件数、最低可用空间或增长速率门禁。回收 worker 依赖 observer enabled、retention opt-in 和 Host 启动链；关闭建议观察会一并停止回收，原客户端仍可能继续写入。

每 tick 串行处理至多四个目录，单个处理包含文件读取、哈希和本机占用核对，所以不能把它当作固定每秒四个的吞吐保证。目录数超过 20,000 时整轮抛错，后续处理与本次状态落盘被跳过；积压越大反而可能完全不能回收。新目录优先入队也需要明确防饥饿预算。

原子隔离后的 `.agent-hub-retired-*` 不在普通目录扫描范围内；已有 retirement receipt 会返回 pending，达到 64 个未决意图又会阻止新回收。保护未知删除结果是正确的，但必须有按原意图核对实际状态的恢复流程，不能永久停在保护状态或盲目重放。

不能笼统声称所有上游版本都没有限制：当前官方 main 已支持 `[rollout_trace] max_payload_bytes` 与 `max_bytes`，默认分别为 64 MiB 单体和 256 MiB 单 bundle，并采用压缩分片，见 [官方配置说明](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md#L134-L169)。这不等于现场旧二进制已经支持；单 bundle 限额也不限制整个目录不断增加的 bundle 数。现有 reader/retention 仅支持 schema 1/2 和既有 JSON 布局，不能只升级写入端就宣称兼容新压缩格式。

### 5. 可观测性与回归样本没有覆盖实际失败

worker 状态只有进程启动以来的尝试次数和最近 16 条结果，缺少各类唯一对象数、字节、最老年龄、入盘/出盘速率及最后成功扫描时间。外层 unavailable 只发给父线程，不保存原因；初始化异常也没有持久错误原因。Host 存活、开关为 1 或旧状态文件存在都不能证明正在回收。

现有回收测试夹具直接把 Schema 1 的 `rollout_ended` 写在最后；源码中没有 `recording_completed` 的回归覆盖。测试证明了旧假设下的安全性，没有证明新事件次序与真实长期积压已经得到处理。

## 为什么此前修复没有根治

- 2026-10-30/31 的修复解决精简建议保存与“旧结果已被较新提取正文替代”的判断，仍要求原 Trace 先跨过封口门禁。
- 2026-11-09 的修复把占用检查提前，降低重复哈希成本，并对部分保留状态退避，见 [历史专项记录](../acceptance/host-lifecycle-cpu-20261109.md)。它没有改变封口条件或增加总量控制；`active-or-unsealed` 仍按五秒退避，误判的已完成记录也走此路径。
- 因此“CPU 下降”“精简建议每聊天只保留一条”“包已升级”“曾清理旧目录”都不能代替磁盘容量验收。

## 实施顺序与边界

### P0：修复兼容判断，恢复可证明的旧数据回收

1. 在 Adapter 内引入窄的 Trace 生命周期判定，保留 Schema 1 的已验证旧路径；为现场 Schema 2 增加经过核实的 recording-completed 路径。分别保存业务状态、writer 完成证据和当前文件身份，不把 completed 标记与任务成功混同。
2. 新封口路径继续核对 manifest/rollout、连续事件、完整行、时间范围和稳定文件。保持来源绑定、最新建议落盘读回、目录/文件身份、占用、隔离后复核和原回收意图校验。553 个样本先做只读分类；实际释放量以完整门禁后的结果为准。
3. 对“rollout 后仍有事件但没有 writer 完成标记”单列 retained 状态；对旧遗留用经验证的 producer 退出、根目录归属、稳定快照和无读写依赖对账。缺少证明则保留，不用年龄替代。
4. worker 对外持久报告 initializing/running/degraded/stopped、固定错误码、最后成功 tick 和扫描时间、心跳、按唯一 bundle 分类的数量与字节。过期状态显式显示 stale。
5. 超大目录改为有界批次与公平调度；超过预算仍处理已验证候选并报告范围，不让单个阈值关闭整轮回收。按原 receipt 对账已完成、未开始、部分完成和未知结果，不签发新的删除意图覆盖旧意图。

### P1：形成独立存储管理与容量控制

1. 将存储管理从“手机建议观察是否开启”中解耦，维护独立生命周期和唯一管理者；Host/客户端不可用时只允许做已获证明的本地对账，不能把历史可读视为运行时可控。
2. 分别计量原始 bundle、活动写入、隔离中间态、未知遗留、精简建议和必要诊断；计数覆盖隔离目录与未决意图。建议初始策略为原始诊断总量 512 MiB 软阈值、1 GiB 目标硬预算，并设置文件数、保留期和卷级可用空间门禁；最终阈值须由实际写入峰值与兼容能力确定。这是提案，不是现有保证。
3. 软阈值启动有界回收并报告阻塞；无法安全释放时限制新增诊断采集，而不是破坏活动文件。只有 writer 端可执行预算，或已验证的独立存储配额，才能保证活动写入的硬上限。单靠下游 worker 不能同时承诺“不碰活动文件”和“任意 writer 下永不超额”。
4. 旧二进制不能动态停录时，明确报告剩余风险：修改未来启动环境不会停止当前进程，需按用户选择正常退出重开，不能强退、外部 truncate、unlink 活动文件或持续重命名根目录伪造轮转。确认支持新 writer 限额和格式后才配置其官方入口，禁止把 main 的配置盲目写给旧端。
5. 未知历史资料需要转存时，先核对无写入/依赖、共享真实挂载、访问隔离及必要加密；清单、原身份、SHA-256、完整读回与恢复验证通过后才释放准确本机副本。转存只解决旧积压，不作为持续向共享盘无限搬运的产品策略；原回执与用户资料独立保护。

### P2：正常建议功能脱离全量诊断记录

1. 正常路径只保存具备准确来源的原生建议结果：完整目标、producer generation、来源 Thread/Turn、请求排序、最新状态、正文摘要/必要正文和安全决定；保持原 owner、新请求失效、取消及未知不回退、六秒租期与零额外模型输入。
2. macOS 现有 `DesktopNativeSampleCapture` 与 `DesktopNativeSuggestionChannel` 可作为起点。复用这些代码不等于已经证明可关闭原 Trace；需逐段核对 producer、来源、安全决定和恢复对原始记录的依赖，并在无全量 Trace 环境完成真实 DEV 验收。
3. Windows 的对应来源与安全采集有既有未通过范围，不宣称可直接复用 macOS 结果。若某版本仍依赖 Trace，作为显式兼容能力保留有界模式；不支持或超预算时仅报告建议暂不可用，保留聊天、命令、草稿、附件与原回执能力。
4. 全量 Trace 改为具名、限时、限额的诊断模式，默认普通运行不持续开启；原配置保留可恢复迁移和回退材料。诊断缓存与原始聊天/附件/操作账本不能共用删除策略。

## 本轮交付与后续入口

本轮已完成源码、实际安装模块、上游一手资料与本机脱敏数据交叉核对，保存五份小型私有证据文件（约 0.53 MB），由本次根因分析主会话负责，在修复及目标机持续负载验收结案后复核其留存必要性。没有创建临时服务、构建目录、工作树或远端任务，也没有删除原 Trace、改正式配置或提交/推送。独立调研职责已结束，无持久测试资源。

下一实施切片应先完成 P0 的封口兼容、错误可见性和真实分类，再实现 P1 的生产端/全目录预算；P2 需要分别证明各平台无全量 Trace 的原生建议来源。截图机器身份与准确运行版本补齐后，将该机分类回填独立现场证据，不能以本机结果代替。
