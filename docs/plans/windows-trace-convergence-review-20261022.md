## 1. 先明确到底要交付什么

最终要交付的是：**用户一次安装／升级 Host Connector 和 Skill，默认持久开启 Trace，手机能可靠查看原 Codex 桌面已生成的下一步建议，并采用到草稿；Windows 与 macOS 都保持原有功能，最后统一发布到几台电脑。**

Trace 的作用是提供原桌面生成的建议来源。普通消息、任务进度、完成和错误反馈由运行时通道提供，并非必须开启 Trace 才能获取。开启 Trace 也不保证每轮都有建议：还需要桌面实际生成预测、来源轮次正确、原桌面运行时可核实。采用建议只修改草稿，不自动发送。安装沿用已有授权，简要说明本机记录范围和关闭方法，不重复增加授权环节；开发者的 Xcode／进程诊断不应成为普通用户的安装步骤。

**现在没有完成的是“新版 Windows 普通运行下的真实业务闭环 → iPhone 真机业务 → 正式发布”。已经完成的源码检查、原生测试和打包不能替代这条闭环。**

当前执行实际上在几个不同问题之间切换，却一直被笼统称作“Windows 收尾超时”。这造成了重新构建、重新绑定证据、等待手机、再返回 Windows 的循环。需要先拆开问题，再按真实依赖推进。

## 3. 必须分开的五个问题

### P0：旧 Windows 验收服务没有完整退出——眼前的直接阻塞

**现象：**停止调度任务后，外层 action 退出，真正的 launcher／Host 仍存活。新旧实例不能占用同一验收端口或同时写同一状态，因此新版启动被挡住。

**已有代码证据：**

- 正式 `scripts/windows-host-task.ps1` 的 `Stop-HostProcessTree()` 不只调用 Scheduler Stop。它还核对并持有本实例进程对象，停止 supervisor、更新所属后代、共用截止等待，并处理仍存活的所属进程。
- `packages/codex-adapter/windows/host-launcher.cs` 已创建带 `KILL_ON_JOB_CLOSE` 的私有 Job，先把子进程加入 Job 再运行。不能再把“增加一个 Job Object”当成尚未实现的根治方案。
- 当前私有验收任务额外使用 `task-action.ps1`：PowerShell 启动 launcher，再循环采集日志和等待它退出。**这条任务的 action 与正式产品直接以 launcher 为 action 的拓扑不同。**

**最可能的机制，但尚待当前原件确认：**停止只到达了外层 PowerShell；launcher 仍存活，持有的 Job 尚未关闭，后代自然没有因此全部退出。这与最新回报一致，但不能仅凭源码断言 Scheduler 的具体终止规则、Job 成员或句柄状态，也不能直接认定正式服务的停止实现有同样缺陷。

**解决办法：**先对照实际 Task action、唯一启动实例、launcher 的 Job／持有句柄及停止时间线，确认停止究竟作用在哪一层。若是验收包装层的问题，修正验收入口，使它使用与产品一致的生命周期，证据采集移到服务之外。复用／抽取已有按实例停止逻辑，参数明确限定验收 Task、配置和端口；不能把固定正式 Task 的脚本原样用于清理验收现场。只有发现产品生命周期本身缺陷，才修改产品。

**验收：**在原生 Windows 对准确隔离实例做一次完整启动—停止—再启动：旧 launcher、supervisor、Host 和所属 helper 均取得退出证明，管道关闭、验收端口释放，无旧 writer；再启动只有一条新链。正式 Host、原 Codex 和业务执行器保持。单纯 Task 显示停止、父进程消失或 kill 调用成功均不算通过。当前失败保留；后续操作先核对现场，不重复旧 Stop 或按历史 PID 清理。

### P1：原 A/B 未加载与找不到 owner——本项已闭环

2026-10-23：用户单独授权的 P1 已完成最小修复与真实验收，见 [P1 原 owner 专项](../acceptance/windows-original-owner-20261023.md)。补丁提交 `e46c706`，完整 `pnpm check` 通过；本机统一包的真实产品桥接让 B 从 fresh 无 owner 经一次打开／一次固定同步恢复，随后同连接 fresh A/B 均取得原 local owner 与完整 canonical 快照，原完成轮／输入摘要一致。Main 独立审计通过。正式服务与 macOS 保持，未要求用户操作；其余阶段不自动推进。

**原因与边界：**独立元数据连接取消归档后，未同步原桌面的归档抑制／会话缓存。普通导航只派发路由；B 导航已到达但没有会话／owner，原桌面正常取消归档又因“无已归档 rollout”提前退出。本次固定同步加原 URI 已实测恢复 B；没有直接读取内部集合或做 hint-only 对照，不推广成所有历史失败的唯一内部原因。owner 不足时在 Native Trace 准备前拒绝是正确行为。

**最小实现：**仅 Windows 显式打开且当前无 owner 时，从同一 Host 的新鲜完整官方目录确认唯一准确目标且 `archived=false`，发送固定 `thread-unarchived` v1 元数据提示，再走原 URI 和现有 fresh owner 等待。目录未知／已归档／重复／错误目标不发提示；不伪造 owner、不写历史、不做归档循环或新模型输入。macOS 不进入新分支。

**真实结果：**B 一次产品打开约 7.983 秒确认原 owner；同连接 fresh A/B 分别约 17.68ms／7.86ms，均为原一完成轮／一输入。A 文件在本轮前后未变；B 仅正常追加一条 settings，原前缀保持。9 个保护角色创建身份／路径与 3 份原 DEV 配置匹配，没有重启 GUI／DEV／正式服务。Main 校验 48 个证据 payload、对照统一 ZIP 核验 1,268 个程序文件，并独立 HTTPS 核对 A/B 可控和输入摘要。

**观测限制：**本轮是独立新包产品桥接路径，未部署新版正式 Host；URI 子进程没有独立 PID／退出码，额外只读前样本工具历史退出未知，后续两次具名查询无匹配进程。产品 reader 的 exit／close／双路 EOF 与外层 exit／close=0 已观察。P2、手机、其他机器与整体发布均不据此通过。

### P2：真实 Windows Trace 固定预算读取——本项已闭环

2026-10-23最终结果：P2已闭环。实际Host/C#数字原件确认重复完整父路径CreateFile是主要工作，最终修复在单B内共享私有根上方namespace锚点；私有根及后代仍逐项鲜开，完整前后身份/ACL、来源和所有预算保持。候选4bb2fec的有效原生覆盖168项分次通过，普通真实13正例/2拒绝/35秒无人工接口读取及恢复全部通过，完整响应4.965–5.864秒。桌面独立后核对的原A/B输入、owner、GUI/执行器/Host身份及配置保护均保持。有限结果绑定当前GUI8120和本次产物，不作为长期SLA或历史唯一代码变量增益；正式服务／macOS／手机及下一项未推进。见[最终结果](../acceptance/windows-trace-budget-result-20261023.md)及[P2历史专项](../acceptance/windows-trace-budget-20261023.md)。

**已确定的历史瓶颈：**某次独立同代请求在约 4003.52ms 触发准备阶段截止；原生检查等待占主要时间，纯解析仅约 2.98ms。更早样本也显示重复发现、路径检查和原生往返成本高。等待区间包含调度、IPC、C# 与 OS 工作，不能直接称为磁盘慢、杀毒软件或 GC 问题。

**已实施方案：**准备／确认分离、请求内收据复用、有界批处理与原生工作优化、后台能力提示及进程退出处理；当前候选的原生测试已通过。Windows 仍保留 prepare/commit 各 4 秒、共享 7 秒、HTTP 总计 8 秒、单原生命令 750ms、最终校验后 6 秒租期。普通真实读取已在本次当前Windows环境通过，具体范围与限制见本节最终结果。

**原定验证策略（已按本次矩阵执行）。** P0／P1 满足后，使用没有诊断预加载的新版普通 Host 跑固定业务矩阵。若再次失败，按具体请求的 owner、prepare、commit、最终校验或清理阶段归因，只补缺失的一段证据。若仍证实全目录发现／完整校验工作量过大，才评审进一步缩小发现范围的定位契约；该契约必须能证明最新失败、未完成与新增记录没有遗漏，不能用旧缓存绕过校验。

**验收：**原定 13 个普通正例均正确返回且各自小于 8 秒；2 个错来源／错轮次拒绝场景返回 409，不带建议或有效租期；覆盖六秒后的租期续读、混合 A／B、35 秒无接口读取的空闲及空闲后恢复。正文、四个来源 ID、最新版本和租期正确，无额外模型输入。记录实际最大延迟及阶段耗时，不把有限样本包装成长期 SLA。

### P3：历史 21.67 秒收尾异常——根因调查，不能再与 P0/P2 混为一谈

旧失败发生在 `desktop-trace-lifecycle` 的 `slow-operation` 合成场景，子进程是故意不响应的 Node fixture，**没有执行真实 C# Trace 读取**。15 秒外层 watchdog 对应约 21.67 秒实际用例时长，结果文件为 0B。后续保持原主要监督边界的三次最小诊断约 1.48–1.56 秒完成，没有重现。

已查到的旧测试缺陷包括：多段等待预算与外层期限不一致；条件为真时可能遗漏超期检查；把 PID 不在当作完整回收；末尾才写结果导致强退时丢证据。当前源码已有截止前后检查、阶段记录及结果发布改进。**这些是已发现并处理的缺陷，不足以证明旧 21.67 秒的唯一 OS 根因。**

后续若仍需归因，复用现有最小计时工具和生命周期测试，只补尚缺的区分证据：

| 要区分的原因                 | 需要放在同一次运行里的时间点                 | 证据指向的修复                       |
| ---------------------------- | -------------------------------------------- | ------------------------------------ |
| timer 实际派发晚             | 计划到期、回调进入、事件循环延迟             | 移出阻塞工作或修正监督／截止判定     |
| 已请求终止，但进程迟迟不退出 | 发出终止、准确创建身份、内核退出时间／码     | 修持有句柄、退出责任或阻塞操作的收尾 |
| 进程已退出，管道仍被持有     | 内核退出、ChildProcess exit、三路 EOF、close | 修管道／句柄所有权和释放顺序         |
| 留证 I/O 或报告进程拖延      | 写入开始／结束、报告进程退出、外层监督事件   | 报告与被测进程解耦，保留部分结果     |

跨进程单调时钟分别记录并建立关联，不直接相减；原生等待与包含它的总区间不能重复相加。任何复现必须先写明要区分哪个假设、固定运行次数和停止条件，不能一直重跑直到绿。原始数据没有采到的事件不能事后补造。

**完成标准分开写：**“历史唯一原因已确定”必须有对应失败的因果证据；“当前实现退出契约已验证”则按受控慢响应、强退、管道与完整回收场景证明。后者通过不能自动关闭前者。若无法恢复原现场，保留“历史未归因”的明确结论及剩余风险；是否接受该状态用于正式发布须单列裁决，不能暗中删除用户要求的根因调查。

### P4：iPhone 的真实产品验收——不能把通道检查算成功能通过

用户已完成 Xcode 登录、设备重启和 UI Automation 系统验证。最近通道证据已到达 setUp 的预期跳过，业务仍未执行。此时继续围绕“是否解锁／是否登录”重复排障没有当前证据支持。

**解决办法：**Windows 请求与来源都就绪后，通过 Xcode／CoreDevice 的 Wi-Fi 连接运行准确的独立验收 bundle。运行前一次核对设备、签名、安装目标与原 App 清单；以实际 build/test 退出和测试断言判断，不能单靠 No Accounts 文本下结论。基础安装／启动／通道检查可独立完成，依赖真实 Windows 数据的业务必须等 P1/P2。

**验收：**四轮 A／B 建议展示，采用、撤销、追加、替换、用户编辑保护以及不自动发送；最后在桌面独立核对输入数、正文和轮次没有增加或串用。保留正式版、原 DEV 版及其数据，完成后恢复本任务测试来源的原归档状态。当前 QA 工具只投影两条真实测试来源，本轮不因此宣称全目录浏览已验收。A6 继续暂停。

## 4. 为什么会进入循环，流程怎样收敛

| 循环来源                                      | 已发生的表现                                                                                 | 应采用的改法                                                                                |
| --------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 一个标签混装多个故障                          | 合成退出超时、真实读取截止、owner 缺失、服务停止和 Xcode 通道都被叫作“收尾问题”              | 固定 P0–P4，每条失败必须标明属于哪一层                                                      |
| 验收环境逐渐偏离产品                          | 私有 PowerShell action、一次性绑定器与采集器不断增加；采集器还曾把历史 helper PID 当固定条件 | 优先复用产品生命周期，采集器只观察；用当前实例身份，不锁死历史 PID                          |
| 辅助证据串成过长前置链                        | Windows 停在包装层时，手机业务及发布一直等待，已通过的 Native 又面临重绑                     | 前置门槛只检查本层必需条件；测试结果按受影响代码范围复用                                    |
| “必须同一个 helper PID”可能与生命周期契约冲突 | 空闲退出／自然换代会让前后 PID 不同                                                          | 先明确产品允许的换代行为；验证旧实例完整退出、新实例同产物且无重叠，不把 PID 永远不变当目标 |
| 状态记录过期、版本混杂                        | 私有草稿还写新版 Native 待跑，原始新结果已通过；不同文件里的“当前”对应不同候选               | 一个当前总表引用原结果；历史只追加，不以旧待办重新派发已完成工作                            |
| 缺少回到具体问题的规则                        | 失败后又打包、扩验证、换入口，难以判断距离完成还有多远                                       | 每轮只解决一个失败机制，先最小验证，再对受影响层回归                                        |

这里“复用结果”必须有范围依据：纯文档或证据读取格式修正，不必重新跑完整 Windows 原生套件；产品逻辑、相关依赖、编译产物或运行路径变化，则重新验证受影响部分并履行仓库要求。旧结果永远绑定原指纹，不能改成新版本的结果。

拟改验收标准（例如允许符合产品契约的 helper 换代）必须在运行前写清理由及断言，不能在失败后删掉条件筛出通过。
