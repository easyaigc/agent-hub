## Saved-file behavior and the missing adapter

The current read-only parent iOS `VoiceInput.swift` permits an explicit saved-file retry after desktop failure, verifies that the file bytes still equal the original recording, then calls `LocalRecordingTranscriber`. `LocalVoiceInput.swift` uses iOS26 `SpeechAnalyzer.start(inputAudioFile:finishAfterFile:)` with `DictationTranscriber`; the older/unsupported-language branch uses `SFSpeechURLRecognitionRequest`. This does not reopen the microphone. The latter branch requests on-device recognition when the recognizer supports it; phone-local therefore does not establish universal offline behavior. Speech authorization, generation/draft validation, failure preservation and local resolution of the original pending record are separate from a new desktop submission. The current parent iOS additionally has explicit `discard()` and labels the failed/finishing close action “discard recording”; the child's older iOS reference still has the previous end-wait label. Both source fingerprints and that difference are recorded privately; current-parent semantics are the comparison reference.

Android's actual `NativeVoiceCapability.canTranscribeSavedRecording` remains false. `NativeSystemVoice` exposes only start/finish/cancel for live recognizer capture, and its intent has no file input. `RecognitionSupport` is consumed for language/route information, without establishing a mandatory saved-file source contract. The Android build has no bundled file-ASR engine or explicit no-microphone file provider. Existing Host prepare/upload/query operations transcribe the original through the selected computer and keep their original ID; they are not a phone-local adapter.

The platform extra does not fill that contract: Android documents that an unsupported `EXTRA_AUDIO_SOURCE` can open the microphone, and the older audio-inject extra may have no effect. Passing a saved file to this optional interface would not prove that the file was transcribed. See [RecognizerIntent audio-source contract](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE), [RecognitionSupport](https://developer.android.com/reference/android/speech/RecognitionSupport), and [Apple file recognition request](https://developer.apple.com/documentation/speech/sfspeechurlrecognitionrequest). This stage introduces no file adapter, capability claim, model download or substitute microphone experiment.

The adjacent `stage19-saved-file-dependency.json` specifies the missing narrow platform/storage contracts and acceptance conditions as a proposal, not executable functionality. It requires a provider that guarantees file-only input, preserves authenticated original bytes and remote attempt/receipt identity, has explicit locale/network capability, cancels only its local recognition, and uses the current original-target/draft/generation guard. Applying recognized text needs a separate storage-owner local-resolution receipt so the old unknown desktop operation is not discarded or resubmitted. No Main/Session/transport API expansion is implemented here.

The current Session composer and question authority closures capture the original selected provider. A phone retry from a desktop-started flow therefore retains that original consent condition as well as target/draft/connection checks. This stage preserves that stricter boundary. A future file-only adapter that remains usable after desktop-sharing revocation needs a parent-reviewed split between local draft authority and desktop submission consent; it must not silently bypass the existing closure.

## Independently implemented interaction corrections

The close control now says “discard recording” after failure or while finishing, matching the current parent iOS explicit-discard intent. A distinct desktop-provider “end waiting” button detaches through a preserving cancel path in those states, including retaining provisional original PCM/metadata if sealing was incomplete. That button does not call the explicit-discard terminal port or remove the original. Live system speech has no saved audio and keeps its existing explicit partial-text fill/discard actions. Initial requesting/listening cancellation and the separately explicit “record again” discard flow retain their existing semantics. Ending waiting never says that the remote operation was cancelled. The extra visible preserving action is an explicitly registered Android UI difference: current iOS has a preserving `cancel()` API but its strip exposes discard there. Parent must review common-surface alignment; no iOS/A6 change is made here.

The existing “record again with phone” button now invokes a named preserving action. It cancels only the old controller work, changes generation and starts a new explicitly selected live phone capture against the same original draft. A sealed unknown original remains stored and offerable with identical ID, manifest, bytes and attempt flags; no terminal marker, Host query/upload, saved-file transcription or default-provider write is performed by the switch. A provisional/in-flight recording, failed discard or changed authority cannot borrow this action. The existing explicit-discard `rerecordWith` contract and its tests remain separate; the phone fallback UI no longer calls that path.

The final record-again button exposes disabled semantics and the normal disabled color when its authority or discard state prevents action. A bounded composer can scroll the shared voice strip to its recovery controls. When an outer question/sheet gives unbounded vertical constraints, that outer container owns scrolling; the strip avoids an infinite nested scroll. Existing 48dp actions, compact layout, appearance tokens and permission-registry lifetime remain in use. The labels use the current parent's already translated discard/end-wait/phone-recording catalog keys; no central catalog file is changed here. The child's older catalog alone is not a bilingual build candidate.
