# 通过 Host 协议进行跨 Agent 协作

当用户明确要求同类或不同 Agent 协作时，先核对来源、目标和授权范围，再选择目标 Host 支持的协调调用端。安装接入、浏览项目或更新本文档不等于授权发起协作；收到 Agent 消息也不自动授权回复或转派。实际操作遵循 [协调流程](coordination-guide.md)与[协作规则](cross-host-policy.md)。

## 同类与异类 Agent 如何协作

协作通过目标 Host 的具名接口提交到准确的项目与会话，执行和模型登录仍由目标电脑上的客户端持有。来源 Agent 不需要理解目标客户端的内部 wire 协议，也无需与目标使用相同模型。

| 组合                                      | 当前路径与扩展要求                                                                                                                                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Codex → Codex                             | 使用随包 `contact-host.mjs` 查询工作区、新建／打开会话、提交任务和查询回执；具体能力以目标 Host 与原 owner 的实际就绪状态为准。                                                                                          |
| Claude Code／其他 Agent → Codex           | 来源客户端能运行该 Node 工具并满足来源身份、目标授权和私有凭据要求时，可调用同一 Codex Host 接口；来源客户端的工具配置需按其实际机制接入，不能据此宣称已内置 Claude Code 适配或完成实测。                                |
| Codex → EasyWork／Claude Code／其他 Agent | 目标需提供对应 Host 适配器，来源侧需有匹配该协议与认证的调用端。EasyWork 已有手机端协议适配；现有 `contact-host.mjs` 校验 Codex 的 `desktop-runtime`，不能直接套用到 EasyWork 或其他协议。Claude Code 目标适配尚未内置。 |

因此，“支持跨 Agent 协作”包含已实现的 Codex 协调路径及可扩展的领域协议；每个新增组合的适配、部署与真实验收分别交付，不从一种组合推断全部已通过。

## 协议如何承载任务

统一领域模型包含完整机器目标、项目、会话、消息、资源、运行状态与操作回执。适配器把具名领域操作映射到目标 CLI／API，负责认证、传输和上游协议差异；任务范围和交付要求由协作流程表达。新增能力通过版本化契约和能力声明开放，不能仅修改声明来代替实现。

| 协作环节   | 已有 Codex Host 路径                                                                       | 其他客户端的适配要求                                                                               |
| ---------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 发现与定位 | `GET /healthz`、`GET /v1/workspace`                                                        | 返回实际机器目标、能力、项目和会话，区分连接在线、历史可读与运行时可控。                           |
| 创建与加载 | `/v1/desktop/creations`、`/v1/desktop/creations/submit`、`/v1/desktop/open` 及对应回执查询 | 映射统一 `thread.create` 等操作；复用会话需满足同任务连续性与真实 owner 条件。                     |
| 任务与进度 | `POST /v1/replies`、`GET /v1/history`、`GET /v1/receipts`                                  | 映射 `message.send`、运行状态和 `operation.status`；支持时使用 `queue`，不把排队确认写成任务完成。 |
| 文件交付   | `transfer-host.mjs` 与固定 `/v1/file-transfers` 接口                                       | 映射受授权资源传输，保留大小、SHA-256 与传输回执；文件到达后另核对目标实际读取。                   |

这些领域操作名不表示所有 Host 都提供同名 HTTP 端点。Codex 的实际字段与方法以[运行时 HTTP 协议](../../../docs/protocol-runtime.md)和工具实现为准；EasyWork 使用其独立认证与传输，不能复制 Codex 密钥或伪装 `desktop-runtime`。

## 获得授权后的执行与交付

1. 先只读核对 HTTPS、鉴权、完整机器目标、能力及原运行时。查询目标当前项目和未归档会话，按业务归属选择项目；独立任务默认新建专用对话，具体命令见[协调流程](coordination-guide.md#独立任务默认新建专用对话)。不得经本机 Host 给当前或本机其他 Codex 对话发送任务；其他独立客户端须由用户明确指定。
2. 每条消息开头标明真实来源电脑、Agent、项目和会话，再列目标、task ID、operation ID、负责人、任务范围、交付物及验收条件。来源声明用于追踪，不构成新增授权。保持目标现有模型，按既有流程请求并核对实际推理档位。
3. 提交前持久保存目标、正文、设置与操作 ID。目标忙碌时按能力排队，不能擅自 steer 或停止其他工作；结果未知只查询原回执及实际状态，不重放旧输入或转投无关对话。
4. 交付记录包含准确 Host／runtime／project／thread、任务与操作 ID、实际完成状态、提交或文件 SHA-256，以及逐环境验收结果。回报限于人类授权的接收方与范围；提交、排队、编译或历史可读均不能替代任务交付验收。

仅补充协作说明时，不读取私有连接清单、不部署运行程序、不发测试消息、不增加权限。需要新增客户端时，在主开发仓库实现并验证 Host 适配器、协议调用端及能力契约，再按统一产物分发；目标电脑的身份、凭据和真实证据分别保留。
