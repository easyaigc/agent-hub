## Confirmed difference and remaining diagnosis

Parent candidate `6148da1a` / App `5b6a816d` / runner `d9daabf3` failed the zero-launch Home audit with expectedHome `com.android.settings`, actualOwner `com.google.android.apps.nexuslauncher`, windowReady true, eight milliseconds and different-owner. The original operation was not reserved or launched; no Main, picker or grant occurred. Parent separately reports shell HOME resolution as the launcher. Those are different query identities; shell output is not App UID proof. The old diagnostic saved only the expected package, so the actual Settings component and App-visible HOME list were not captured. FallbackHome/package visibility is a supported hypothesis, not a proven unique cause.

The current App source Manifest and the hash-matched parent App24 packaged Manifest have no MAIN/HOME query. Android documents package visibility filtering and intent-signature declarations in `<queries>`; see [visibility declarations](https://developer.android.com/training/package-visibility/declaring) and [filtering behavior](https://developer.android.com/training/package-visibility). An AOSP [Settings Manifest](https://android.googlesource.com/platform/packages/apps/Settings/+/0ea1d883ec/AndroidManifest.xml) declares a low-priority HOME FallbackHome; its [implementation](https://android.googlesource.com/platform/packages/apps/Settings/+/53ea491d276/src/com/android/settings/FallbackHome.java) queries the real Home after unlock. These sources explain why App and shell observations require separate evidence; they do not prove the precise prepatch runtime cause.

## Narrow change

`apps/android/src/debug/AndroidManifest.xml` declares exactly one query: ACTION_MAIN plus CATEGORY_HOME. It applies to debug builds, including the existing acceptance debug identity. It adds no permission, package-name visibility, provider authority, wildcard or QUERY_ALL_PACKAGES. The main/release Manifest is unchanged. Compilation separately checks the query is present in the debug target App's packaged Manifest and absent from the release merged Manifest; declaring it only in the runner would not establish target-App visibility.

Acquisition and the zero-launch Home audit share the existing beforeMain boundary. A new App-UID-only resolver observation records the MATCH_DEFAULT_ONLY component, a bounded visible-HOME list and count, and a flag-zero lookup for comparison only. It never selects another candidate or uses the flag-zero result as a fallback. Diagnostics contain only bounded package/component/UID/boolean metadata, no page content, shell command or adopted shell identity.

The resolved default must exactly match a visible enabled/exported component from that same App query. Settings, framework resolver package, FallbackHome/ResolverActivity/ChooserActivity components and self/runner-owned components refuse even if an owner string could match. Missing, oversized or inconsistent candidate information also refuses. No launcher package is hardcoded as an accepted owner. Only after this validation does the unchanged five-second refreshed-root readiness wait compare the exact resolved package; any different owner still fails immediately. Both pre/post P9/no-Main/exact-grant gates remain in place. No original receipt is reserved by either resolver diagnostics or the audit.
