# Notification recovery v2 — server candidate

Status: implemented source and auxiliary candidate after design `4df98a64`; Android v2 wire/journal/monitor integration is the next stage. No deployed Host, native device, model or vendor result is claimed.

`packages/protocol/src/notification-recovery-v2.ts` defines independent v2 intent/canonical/page contracts. `packages/notification-runtime/src/recovery-v2.ts` implements reservation/settlement, original-ID query, per-device monotonic generations/absent-device tombstones, a bounded original log and explicit reset snapshots. The existing publisher integrates these into the same atomic device/state file. `apps/host-agent/src/notification-recovery-routes.ts` serves only the three fixed routes defined in the design, after normal Host authentication. It rechecks the complete current target after body reading and rejects duplicate/unused query/body fields. It never forwards an arbitrary route/method.

First capability activation persists the epoch and internal disk format 2; the former writer's `version !== 1` gate blocks unsafe downgrade. V1 files still load and v1/iOS wire remains unchanged for devices that have not adopted v2. Adopted device IDs reject all generationless v1 writes. Capability is emitted only after initialization succeeds; no new generic health capability was added.

Complete original intent and reservation persist before device effects. Device state and final receipt publish atomically. Startup settles surviving reservations from those exact originals, rejecting superseded generations. New attempted IDs cannot reuse a generation already represented by a receipt, including rejected requests. Registration/preferences preserve preference-generation monotonicity; explicit off may fence an older/unknown registration through a greater subscription generation. The prior preference revocation floor still prevents restoration of stale enabled preferences. Applied local revocation and pending relay cleanup stay separate; application never promises vendor removal or device arrival.

Uncertain v2 publication poisons mutations/receipts until restart reads durable state. Shutdown releases its own writer lease even on failure. Old revocation microtasks are generation-checked before they can disable a newer enabled generation. Relay replies retain their original object checks. Tests use owned fake relay services only.

V2 records an entire observed batch before v1's independent last-512 pruning. It assigns a sequence once in the same original entry and keeps the first raw payload/fingerprint; an account-only Codex observation change neither rejects nor rewrites it. Other content changes conflict. The log is contiguous and bounded; pruning raises an explicit floor. Pages bind epoch/generation/after/through and include each scanned original with a Host filtering disposition. Suppressed originals are not silently skipped. Both count/byte limits apply. The finalized page limit is **256 KiB** (32 originals, 2048 active IDs), adjusted from the design's tentative 128 KiB for the active-ID envelope; pages dynamically shrink to fit.

Retention/epoch gaps return `reset-required`. Only a separate full `feed-reset` intent with durable gap acceptance prepares a bounded original snapshot. Original receipt, snapshot hash/baseline and expiry survive restart. It cannot certify pruned history or clear P7. Expiry/capacity never auto-rebases. Until the parent wires explicit reset/off handling, clients remain blocked; old v1 unknown cannot be retroactively resolved.

Schema and five cross-language vectors are frozen by `scripts/notification-recovery-v2-contract.mjs`. Run `pnpm build`, the generator without `--write`, then `node --test scripts/notification-recovery-v2.test.mjs scripts/notifications-smoke.mjs`. New tests exercise production canonical/receipts, real atomic fixture files/restarts, the actual fixed HTTP dispatcher on loopback, byte/count feeds, filtering, reset snapshots, corruption/capacity, v1 compatibility, account metadata and delayed fake-relay replies. They are auxiliary, not real Host/phone/model proof. The root check is also run; its central parity gate remains coordinator-owned. Parent should append the new contract/test commands to that check chain while preserving existing commands.

Host state/key/receipts are machine-local and must not be copied between computers or identities. The Android local journal is a separate next stage; its migration must exclude active keys/subscriptions/cursors and preserve unknown originals. No second mobile migrator, shared app navigation, native manifest or central table was edited in this server stage.

Freshness refinement: `activeIds` retains unresolved actionable originals across owner loss/restart, matching v1. Host freshness only controls item eligibility. An actionable `stale` item is waiting for verification, not a terminal suppression: Android must keep the page cursor, preserve completed results, and refresh the captured original window before continuing. Non-actionable stale items are expired under the existing ten-minute policy. No stale/read response alone resolves a pending request. Only a live source observation can mark it inactive; the new Node restart/owner-loss regression covers this distinction.

V2 active-set scope is all actual unresolved actionable originals on the target, independent of notification kind/badge filtering. This prevents a preference change from clearing P7's unread notices. Item disposition checks actual inactivity/freshness before preference filtering: a current filtered original can still reconcile through P7 while its alert is suppressed; an inactive/expired original cannot be revived through that path. V1's existing filtered active set remains wire-compatible and unchanged.
